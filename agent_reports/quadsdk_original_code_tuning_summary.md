# Quad-SDK 元コードからの変更・チューニングまとめ

## 1. この資料の目的

Quad-SDK の元コードに対し、現在までに何を変更し、なぜ変更したのかを整理する。

対象は Go2 の MuJoCo シミュレーションであり、最終目的は平坦路面上の穴に対して次を成立させることである。

1. Terrain Map 上で穴または接地不能領域を判定する。
2. 名目足場を、安全かつ脚が届く足場へ補正する。
3. 補正後の足場を NMPC へ渡し、胴体運動と接地反力を計算する。
4. 安全な足場がない場合は、危険な名目足場を使わず減速・停止する。

30 cm の穴を越えること自体は最終目的ではない。30 cm は現状の方式に対するストレス試験であり、安全限界を調べるための条件である。

## 2. 結論

現在までに行った変更の中心は、NMPC の数式変更ではない。

- Quad-SDK をこの環境で正常にビルド・実行するための修正
- 穴に対応しやすくするための歩容、探索範囲、予測時間、地形表現の調整
- 足場選択の成功・失敗を観測可能にする診断機能の追加

である。

Go2 用 NMPC では、足場位置は最適化変数ではなく、あらかじめ Local Footstep Planner が決めた固定パラメータである。NMPC は、その足場をモーメントアームとして使用し、胴体状態と4脚の接地反力を最適化する。

安全な足場が見つからない場合に安全停止する制御ロジックは、まだ未実装である。これは Phase 2 以降の対象である。

## 3. 元コードから変更した内容

### 3.1 ビルド・実行を成立させるための修正

| 対象 | 元の状態 | 現在の状態 | 変更理由 | 分類 |
|---|---|---|---|---|
| IPOPT linear solver | `ma27` | `mumps` | MA27 は Coin-HSL に含まれるが、このPCには Coin-HSL が導入されていないため。MUMPS は現在の IPOPT で利用可能 | 環境適合 |
| `stand_cmd_vel_threshold` | `0.1` | `0.05` | コードが `cmd_vel.norm() > threshold` という厳密な `>` 比較であり、0.1 m/s 指令が歩行判定に入らなかったため | 起動条件修正 |
| Pinocchio の CMake / package export | 依存関係が下流へ正しく伝播しない | CMake ターゲットと `package.xml` の依存を修正 | `pinocchio/multibody/model.hpp` が下流パッケージから見つからないビルドエラーを解消するため | ビルド修正 |
| Planner reference | 既定は `gbpl` | `reference:=twist` | Global Body Planner を使わず、`cmd_vel` から Local Planner を駆動するため | 実行設定 |
| Control mode | WALK への切替なし | `control/mode=2` | `robot_driver` に Local Plan を追従させるため | 実行設定 |
| cmd_vel publisher | 必須 YAML なし | topics 用 params file を指定 | パラメータ未初期化で publisher が起動直後に異常終了していたため | 実行修正 |
| Python | ユーザー環境の Python 3.11 が混入 | `/usr/bin/python3` を明示 | ROS 2 Jazzy の Python パッケージと整合させるため | 環境分離 |

#### MA27 から MUMPS への変更の意味

これは NMPC の目的関数、運動方程式、制約条件を変更するものではない。IPOPT が反復計算の内部で解く疎線形方程式のソルバーを、現在のPCで利用可能な実装へ切り替えたものである。

変更前は `ma27` を利用できず NMPC 求解が連続失敗していた。`mumps` へ変更後は、その連続失敗が解消し、ロボットが安定して自立した。これは実験で確認済みである。

### 3.2 穴対応のための歩容調整

| パラメータ | 元の設定 | 現在の設定 | 目的 |
|---|---:|---:|---|
| gait | trot | crawl | 同時接地脚を増やし、穴付近で静的安定性を高める |
| `period` | `0.36 s` | `0.9 s` | 一歩をゆっくり実行し、足場補正後の追従余裕を増やす |
| `duty_cycles` | `[0.5, 0.5, 0.5, 0.5]` | `[0.75, 0.75, 0.75, 0.75]` | 各脚の接地時間を増やす |
| `phase_offsets` | `[0, 0.5, 0.5, 0]` | `[0, 0.75, 0.5, 0.25]` | 4脚を順番に動かす crawl 歩容にする |
| `ground_clearance` | `0.07 m` | `0.10 m` | 遊脚が穴縁や地形へ接触する可能性を下げる |

Quad-SDK は地形を見て gait を自動変更しない。`period`、`duty_cycles`、`phase_offsets` から起動時に固定の接触スケジュールを生成する。したがって、trot から crawl への変更は明示的な設定変更である。

### 3.3 足場探索の調整

| パラメータ | 元の設定 | 現在の設定 | 目的 |
|---|---:|---:|---|
| `foothold_search_radius` | `0.25 m` | `0.70 m` | 名目足場が穴に入った場合に、穴の反対側を含む候補を探索可能にする |
| `foothold_obj_threshold` | `0.6` | `0.6` | 変更なし。`traversability > 0.6` を有効候補とする |
| `obj_fun_layer` | `traversability` | `traversability` | 変更なし。足場判定に Terrain Map の traversability を使用する |

探索半径を広げても、脚の可到達性が保証されるわけではない。現在の足場探索には IK 制約がなく、NMPC にも関節角度や脚可到達性の制約はない。そのため、0.70 m は探索可能範囲であって、安全な脚到達範囲を意味しない。

### 3.4 NMPC の予測時間調整

| パラメータ | 元の設定 | 現在の設定 |
|---|---:|---:|
| `horizon_length` | `26` | `40` |
| 時間刻み | `0.03 s` | `0.03 s` |
| 予測時間 | `0.78 s` | `1.20 s` |

`26` から `40` への変更で穴通過時の挙動が改善したことは実験事実である。

一方、「予測時間が gait period より長くなければならない」という必須条件はコード上にはない。改善した正確な機序は未確定であり、今後、目的関数の内訳、制約違反、slack、IPOPT status を記録して確認する必要がある。

### 3.5 穴を表す Terrain Map の変更

元の試験地形から、穴をまたぐ三角形を持たない水平ストリップ状の PLY メッシュへ変更した。

- 物理シミュレーション上の穴幅: `0.30 m`
- Terrain Map 上の接地禁止帯: `0.40 m`
- 差分: 穴の両側へ `0.05 m` ずつ安全余裕を付加

穴領域にはメッシュ面が存在しないため、生の高さレイヤー `z` は NaN になる。現在確認済みの静的 PLY 地形では、フィルタ処理後の `traversability` も穴帯で NaN となり、足場候補から除外される。

ただし、実機の LiDAR や深度カメラから作る地図でも未観測領域が自然に同じ NaN 表現になるとは限らない。このリポジトリには実センサ点群から GridMap を生成する完全な処理系がなく、実センサ時の挙動は未確認である。

### 3.6 実験・観測用の変更

| 対象 | 変更 | 理由 |
|---|---|---|
| RViz | 既定起動を無効化 | ヘッドレス試験では不要なため。明示指定すれば起動可能 |
| MuJoCo camera | 追従、距離、注視点を launch 引数化 | 固定カメラで実際の前進距離を確認するため |
| 地面 | 広い平面ワールドを追加 | 10 m 試験で既定地面の端から落ちないようにするため |
| 記録ノード | state、GRF、local plan を CSV 化 | 転倒、移動距離、接触状態、NMPC 更新を定量確認するため |
| 実行スクリプト | 起動順、終了処理、残留プロセス対策を追加 | 再現性のある反復試験を行うため |

## 4. Phase 1 で追加した足場診断

従来の `getNearestValidFoothold()` は `Eigen::Vector3d` の足場位置だけを返すため、その足場が正常選択されたのか、フォールバックされたのかを呼び出し側が判定できなかった。

Phase 1 では、挙動を変えずに次の診断型を追加した。

```cpp
enum class FootholdStatus {
  VALID,
  NOMINAL_OUTSIDE_MAP,
  NO_TRAVERSABLE_CANDIDATE,
  NONFINITE_HEIGHT,
};

struct FootholdResult {
  Eigen::Vector3d position;
  FootholdStatus status;
  double traversability_nominal;
  double traversability_selected;
  double snap_distance;
};
```

各値の意味は次のとおりである。

| 値 | 意味 |
|---|---|
| `position` | 選択された足場位置。Phase 1 では従来と同じ値 |
| `status` | 足場探索の成否または失敗理由 |
| `traversability_nominal` | 名目足場の traversability |
| `traversability_selected` | 採用足場の traversability |
| `snap_distance` | 名目足場から採用足場までの水平補正距離 |

既存の `getNearestValidFoothold()` は、新しい関数が返す `position` だけを返すラッパーとして残している。したがって Phase 1 は診断情報の追加であり、制御挙動は変更していない。

足場選択テストは 17/17 件が成功している。別の既存テストには `horizon_length=26` を固定期待する記述が残っており、現在の設定 `40` と不一致である。これは Phase 1 の変更とは無関係であり、別コミットで修正する必要がある。

## 5. 変更していない制御の中核

### 5.1 足場選択の基本式

Local Footstep Planner は、Raibert 型ヒューリスティックで名目足場を作り、その周囲から `traversability > 0.6` のセルを探索する。

候補評価は概ね次の形である。

\[
J_{foot}(p)
=
\lVert p-p_{nominal}\rVert
+0.5\lVert p-p_{previous}\rVert
\]

- 名目足場に近い候補を優先する。
- 前回の選択足場から急変しない候補を優先する。

この評価関数の本体は変更していない。前方へ強く補正する実験的な評価も一度行ったが、現在は元の評価へ戻している。

### 5.2 Go2 の NMPC

Go2 では 12 状態の simple rigid-body model を使用している。

- 状態: 胴体位置、姿勢、並進速度、角速度
- 入力: 4脚 × 3軸の Ground Reaction Force
- 足場位置: 最適化変数ではなく、Local Footstep Planner が決めたパラメータ

足場位置は、重心まわりのモーメントを計算するためのモーメントアームとして運動方程式へ入る。

\[
m\dot{v}=\sum_i f_i + mg
\]

\[
I\dot{\omega}+\omega\times I\omega
=
\sum_i r_i\times f_i
\]

ここで、`r_i` が胴体原点から足場までの相対位置、`f_i` が各脚の接地反力である。

なお、コード中の `foot_positions_body_` という変数名は正確ではない。実装は `foot_world - body_position_world` を行うだけで姿勢回転を適用していないため、実体は「胴体原点から足までの相対ベクトルを world 軸で表現した値」である。

### 5.3 NMPC の制約

Go2 simple NMPC で確認されている主要制約は次である。

- 離散化した剛体運動方程式
- 接触スケジュールによる遊脚 GRF = 0
- 接地脚の鉛直接地力 `10 N <= f_z <= 150 N`
- 摩擦ピラミッド

関節角度、IK、脚可到達性、穴の traversability は NMPC の制約に含まれていない。

摩擦係数は、設定ファイルの読み込み順では Go2 側の `0.6` が一般設定の `0.3` を上書きすると読める。ただし実行時の確定値は `ros2 param get` で確認する必要がある。

## 6. 現在残っている問題

### 6.1 足場がない場合も名目足場を返す

有効な候補が見つからない場合、元コードは警告を出して名目足場を返す。この名目足場が穴上にある可能性がある。

Phase 1 では失敗状態を識別できるようにしたが、下流はまだ `position` だけを使用している。そのため挙動は元コードと同じである。

### 6.2 Map 外の失敗が足場探索関数へ届かない

`computeFootPlan()` は名目足場が Map 外の場合、`getNearestValidFoothold()` を呼ぶ前に `continue` する。したがって、足場探索関数の戻り値だけを拡張しても Map 外失敗を完全には伝播できない。

### 6.3 可到達性を確認していない

探索半径内の traversability が高ければ候補になり得るが、その位置へ実際に脚が届くかは確認していない。大きな `snap_distance` の足場を選んでも、NMPC はその足場を固定パラメータとして受け取るだけである。

### 6.4 `planner_failed` だけでは停止しない

Local Planner は失敗時に Bool の `planner_failed` を publish するが、Robot Driver はこれを購読していない。したがって、Bool を publish するだけでは安全停止にならず、失敗理由も表現できない。

### 6.5 NMPC 失敗時の実際のフォールバック

NMPC 求解が失敗すると、新しい Local Plan は publish されない。Inverse Dynamics Controller は計画が 0.1 秒以上古くなると無効と判定し、Robot Driver は立位関節角への PD hold に移る。

したがって「NMPC が失敗した解の GRF をそのままトルクへ変換する」という説明は正しくない。

ただし、求解自体は成功していても低品質な解が出た場合は別問題である。これを判定するには IPOPT status、目的関数の内訳、slack、制約違反、GRF 飽和を記録する必要がある。

## 7. 次の対策

### Phase 2A: 無効な足場を NMPC へ渡さない

最初に行うべき変更は、足場失敗を安全側へ閉じることである。

1. `computeFootPlan()` 全体が成功・失敗と理由を返す型にする。
2. Map 外の `continue` を明示的な失敗状態へ変更する。
3. `status != VALID` の場合は、NaN、ゼロ、危険な名目足場を足場行列へ書かない。
4. 無効な Foot Plan では NMPC を呼ばず、新しい Local Plan を publish しない。
5. 脚番号、接地予定時刻、名目足場、失敗理由を診断ログへ出す。

### Phase 2B: 制御された停止状態を実装する

足が空中にある状態で即座に STAND へ切り替えると、空中脚へ接地力を割り当てる危険がある。このため停止は状態機械として設計する必要がある。

候補状態は次のとおりである。

- `WALKING`
- `STOP_REQUESTED`
- `WAITING_FOR_ALL_CONTACT`
- `STAND`
- `FAILURE_LATCHED`

少なくとも次を明示する必要がある。

- すでに遊脚中の脚をどこへ着地させるか
- 新しい離脚をいつ禁止するか
- `cmd_vel` をどの時間でゼロへ減速するか
- 全脚接地を実測接触と計画接触のどちらで判定するか
- 最後の正常計画を何秒まで使うか
- 失敗解除を自動にするか、操作者のリセットを必要とするか

### Phase 3 以降

| Phase | 内容 |
|---|---|
| 3 | 穴縁からの安全距離を GridMap 上で明示評価する |
| 4 | `QuadKD2::worldToFootIKWorldFrame` を使い、IK 可到達候補だけを残す |
| 5 | `snap_distance` が大きい場合に減速または刻み歩行へ移行する |
| 6 | Map のタイムスタンプ、未観測セル、実センサ由来データの扱いを追加する |

## 8. 30 cm 穴の位置づけ

30 cm の物理穴に両側 5 cm の余裕を加えると、足場探索上は 40 cm の接地禁止帯になる。

```text
上面図（進行方向 →）

       接地可能面         物理的な穴 30 cm          接地可能面
─────────────────┐                              ┌─────────────────
                 │                              │
                 └──────────────────────────────┘

              │← 5 cm →│←──── 30 cm ────→│← 5 cm →│
              ├────────────────────────────────────┤
              │       接地禁止帯 合計 40 cm        │

Terrain Map:  接地可   禁止       穴       禁止   接地可
                        ↑                     ↑
                    穴縁マージン           穴縁マージン
```

この 40 cm は穴の実寸ではない。内訳は次のとおりである。

\[
0.05\ \mathrm{m}
+0.30\ \mathrm{m}
+0.05\ \mathrm{m}
=0.40\ \mathrm{m}
\]

- 中央の 30 cm: 物理的に地面が存在しない領域
- 左右の 5 cm: 足先を穴縁へ近づけすぎないために PLY 側へ加えた余裕
- 合計 40 cm: Foot Placement が有効な接地点として選んではならない領域

crawl の周期が 0.9 秒の場合、速度指令と1周期あたりの前進距離は次の関係になる。

| 速度指令 | 1周期あたりの前進距離 |
|---:|---:|
| `0.15 m/s` | `0.135 m` |
| `0.30 m/s` | `0.270 m` |
| `0.50 m/s` | `0.450 m` |

したがって 40 cm の接地禁止帯は、特に低速時には複数周期にまたがる厳しい条件である。

評価は次の段階に分けるのが適切である。

- 物理穴 10、15、20、25 cm: 基本性能の確認
- 物理穴 30 cm: 限界付近のストレス試験
- 物理穴 40〜50 cm: 安全停止の確認

## 9. 現在地

現在は、元の Foot Placement + NMPC を穴試験へ適用するために、実行環境、歩容、探索範囲、予測時間、地形表現を調整し、足場選択の診断情報を追加した段階である。

まだ「安全な足場がなければ危険な名目足場を使わず停止する」という要求は満たしていない。次の実装対象は Phase 2A の失敗伝播であり、その後に Phase 2B の制御された停止へ進む。
