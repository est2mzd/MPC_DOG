# 姿勢復帰モードの実装計画

## 試行記録の残し方

- 開発者は、一試行を終えるたびに、その試行だけの結果を `recovery_modes_trials.md` へ追記する
- 各試行の記録は、次の六項目を同じ順序で繰り返す
  - 背景では、直前の試行で分かった問題と今回の変更が必要な理由を書く
  - 目的では、今回の試行で確認することを一つに限定して書く
  - 結論では、成功または失敗と、目的を達成したかを最初に書く
  - 詳細では、初期姿勢と変更値と実行条件と観測値と失敗位置を書く
  - GIF では、寝姿勢または転倒前から復帰結果までが分かる映像を貼る
  - 次への施策では、今回の結論から次の一試行で変えることを一つ書く
- 開発者は、成功試行だけでなく、失敗試行と起動異常も一試行として残す
- 開発者は、複数の試行を後から一つの結論へまとめず、試行直後に一件ずつ追記する
- 開発者は、CSV と動画の保存先と実行コマンドを各試行の詳細へ書く
- `DEVELOPMENT.md` は、姿勢復帰モードの実装計画と試行記録の両方へリンクする

## 第1章 概要

- この計画では、開発者は歩行用 MPC を使わず、判定と寝返りと立ち上がりを順番に実行して転倒姿勢から通常の立位へ戻す
  - 状態判定では、復帰制御器は胴体の姿勢と角速度と高さと関節角を使う
  - 動作生成では、復帰制御器は時刻付きの関節角キーフレームを補間し、各関節へ PD 指令を出す
  - 制御切替では、新しい復帰ノードが既存の歩行指令と新しい復帰指令の片方だけをモータ側へ渡す
  - 安全処理では、復帰制御器は速度とトルクと試行時間を制限し、異常時に `SAFETY` へ移る
  - 引渡しでは、新しい復帰ノードが立位を確認してから既存の歩行指令へ戻す
- 初期条件は、仰向けと左横倒しと右横倒しの三つにする
- ユーザーが指定した復帰シナリオは二つに限定する
  - シナリオ1は、平地上で初期状態から仰向けまたは左右の横倒しに寝ている状態を使う
  - シナリオ2は、立位から階段を走行し、自然に転倒して静止した状態を使う
  - シナリオ1は、うつ伏せを初期姿勢にしない
  - シナリオ2の転倒後姿勢は事前に固定できず、仰向けと横倒しとうつ伏せのいずれにもなり得る
- 復帰動作は、初期条件ではなく途中の段階として整理する
  - 段階1では、復帰処理は転倒姿勢を判定して運動が静まるまで待つ
  - 段階2では、仰向けなら脚を畳んでから片側の脚で胴体を横倒しまで回す
  - 段階3では、横倒しまたはうつ伏せから四脚を胴体下へ入れる
  - 段階4では、低い四脚支持から胴体を持ち上げる
  - 段階5では、直立を確認して既存の立位制御へ引き渡す
  - 段階6では、新しい NMPC 計画を待って走行を再開する
- 低い四脚支持とうつ伏せを計画へ含める理由は、試験の初期条件を増やすためではない
  - 低い四脚支持は、寝姿勢から通常立位へ直接跳ね上げず、安全に押し上げるための中間状態である
  - うつ伏せは、仰向けから寝返った直後と階段で自然転倒した後に現れ得る途中状態である
  - シナリオ2で仰向けだけを処理すると、横倒しまたはうつ伏せで止まった試行を復帰できない

## 第2章 現状と設計判断

### 概要

- 現状の `robot_driver` は、転倒復帰ではなく座位と立位の遷移だけを実行する
- 現状の NMPC と逆動力学は、胴体が立ち、足先が地面側にある状態を前提にする
- 本計画は、既存ノードを変更せず、新しい復帰ノードと起動時のトピック remap で指令を切り替える
- 本計画は、シミュレーション用の自作復帰と実機用の Unitree 公式復帰を分離する

### 詳細

- 現状の `robot_driver` は、`SIT` と `READY` と遷移状態と `SAFETY` を持つ
  - `SIT_TO_READY` は、現在関節角から `stand_joint_angles` までを一秒で線形補間する
  - この遷移は、胴体が立って脚が胴体下へ入る状態を暗黙に前提にする
  - 仰向けで同じ目標角を使うと、脚が空中で開くだけで胴体を反転できない可能性が高い
- 現状の `InverseDynamicsController` は、`RobotPlan` の地面反力と遊脚目標から関節指令を作る
  - 転倒中は、接触方向と支持脚の前提が歩行時と一致しない
  - 復帰中に NMPC を動かしても、寝返りに必要な胴体接触と衝撃をモデル化できない
- 新しい復帰ノードは、既存ノードの外側で状態監視と復帰指令生成と指令切替を行う
  - 既存の `robot_driver` が出す `control/joint_command` は、起動時の remap で `control/walking_joint_command` へ移す
  - 新しい復帰ノードは、`control/walking_joint_command` と新しい復帰指令の片方だけを既存の `control/joint_command` へ出す
  - 既存の local planner が受ける `cmd_vel` は、新しい復帰ノードが出す速度指令へ起動時に remap する
  - 復帰中は、新しい復帰ノードが local planner へ零速度を出す
  - 通常時は、新しい復帰ノードが上流の速度指令をそのまま local planner へ渡す
  - 新しい復帰ノードは、歩行計画が無くても関節位置と速度と PD ゲインを生成する
  - この構成は、`robot_driver` と local planner と NMPC のソースを変更しない
- 実機の Unitree SDK は、`SportClient::RecoveryStand()` を提供する
  - 現状の `UnitreeInterface` は、Sport モードを解放して `rt/lowcmd` を使う
  - 低レベル制御と `RecoveryStand()` を同時に使うと指令所有権が競合する
  - 実機経路は、低レベル制御を停止してから Sport モードへ所有権を渡す別実装として評価する

### 結論

- 元の実装は座位から立位へ戻せるが、転倒した胴体を反転する機能を持たない
- 新しい実装は既存ソースから分離した復帰ノードを追加し、仰向けを含む転倒姿勢を段階的に扱う

## 第3章 復帰手順

### 概要

- 現在の `main` が持つ `SIT` と `READY` と `SIT_TO_READY` と `READY_TO_SIT` と `SAFETY` は変更しない
- 最初の実装は、新しい制御モードを `RECOVERY` と `RESUME` の二つだけにする
- 転倒確認と姿勢判定と寝返りと押上げと立位確認は、`RECOVERY` 内の処理にする
- 計画の破棄と新しい計画の待機と速度の段階復帰は、`RESUME` 内の処理にする
- 復帰失敗では、新しい復帰ノードが既存の `control/mode` へ `SAFETY` 要求を出す

### 詳細

- `RECOVERY`
  - 区分は、新規作成である
  - 目的は、仰向けと左右の横倒しから通常の立位へ戻すことである
  - 最初に低い位置ゲインと速度減衰で転倒直後の動きを静める
  - 次に仰向けと左横倒しと右横倒しを判定する
  - 次に姿勢別の関節キーフレームで寝返りと脚収納と押上げを実行する
  - 最後に姿勢と高さと角速度と関節誤差から立位を確認する
  - 立位を確認した場合は、`RESUME` へ移る
  - 時間切れと状態欠落と関節制限と過大角速度では、既存の `control/mode` へ `SAFETY` 要求を出す
- `RESUME`
  - 区分は、新規作成である
  - 目的は、復帰後の現在状態から安全に走行を再開することである
  - 転倒前の歩行計画を破棄する
  - 新しい歩行計画が届くまで立位 PD を使う
  - 新しい計画を受理したあと、速度指令を零から段階的に戻す
  - 速度復帰を完了した場合は、既存の歩行指令をそのまま通す
  - 新しい計画が届かない場合は、立位を維持する
- 実行順序は、次のとおりにする
  - 新しい復帰ノードは、既存の制御モードに関係なく転倒条件を監視する
  - 転倒条件が一定時間続いた場合は、新しい復帰ノードが `RECOVERY` を開始する
  - `RECOVERY` は、立位へ戻った場合に `RESUME` へ移る
  - `RESUME` は、走行再開を完了した場合に既存の歩行指令を通す
  - `RECOVERY` が失敗した場合は、既存の `SAFETY` 要求を出す

### 結論

- 元の制御モード切替は一つの座位と一つの立位を時間補間する
- 既存の制御モードは変更せず、新しい復帰ノード内のモードを `RECOVERY` と `RESUME` の二つに限定する
- 復帰内部の処理を独立した制御モードへ分けるのは、試験で必要性を確認した場合だけにする

## 第4章 実装単位

### 概要

- 開発者は、復帰制御器と設定と起動と試験と記録を独立した実装単位へ分ける
- 開発者は、既存の `robot_driver` と local planner と NMPC のソースを変更しない
- 実装区分は、新規作成と既存利用と既存修正の三つに分ける
  - 新規作成は、復帰ノードと復帰モードと復帰トピックと復帰設定と復帰 launch と試行シェルと復帰記録である
  - 既存利用は、`RobotState` と `local_plan` と `cmd_vel` と歩行関節指令と `control/mode` と `SAFETY` である
  - 既存利用では、新しい復帰ノードが既存トピックを購読または publish するだけにする
  - 既存修正は、最初の実装では行わない
  - 既存ソースの修正は、新規構成だけでは成立しないことを試験で確認した後に別計画として検討する

### 詳細

- 新しい復帰ノードでは、開発者は状態監視と復帰指令生成と指令切替を一つの新規パッケージへ入れる
  - 新しい復帰ノードは、既存の `RobotState` と `local_plan` と歩行関節指令を購読する
  - 新しい復帰ノードは、既存の `control/joint_command` へ最終関節指令を publish する
  - 新しい復帰ノードは、復帰状態と姿勢分類と試行回数と失敗理由を新しい状態トピックへ publish する
  - 復帰要求は、新しい専用トピックまたは専用サービスから受け取る
- 新しい復帰 launch の remap では、開発者は既存コードを変えず、実行時のトピック名だけを置き換える
  - remap は、新しく作る復帰 launch の実行中だけ有効にする
  - 既存 launch ファイルと既存ノードのソースは変更しない
  - `robot_driver` の関節指令出力は、`control/walking_joint_command` へ remap する
  - local planner の速度入力は、新しい復帰ノードが出す速度トピックへ remap する
  - 上流の速度指令は、新しい復帰ノードの入力トピックへ送る
  - 既存の `control/joint_command` は、新しい復帰ノードの出力専用にする
- 復帰指令生成では、開発者はキーフレーム列と遷移条件をデータとして持つ
  - 各キーフレームは、十二関節の目標角と所要時間と `kp` と `kd` とトルク上限を持つ
  - 左右反転は、別の数値列を複製せず、脚番号と abad 符号の変換で作る
  - 数値は C++ へ埋め込まず、ロボット別 YAML から読み込む
- 設定では、開発者は姿勢閾値と時間切れと再試行回数と関節キーフレームを持つ新しい復帰設定ファイルを作る
  - Go2 用の設定は、`motor_limits.torque` と `motor_limits.speed` より厳しい復帰専用上限を持つ
  - シミュレーション設定と実機設定は、同じ既定値を暗黙に共有しない
- 起動では、開発者は既存 launch を変更せずに含む復帰試験専用 launch と試行シェルを追加する
  - 試行シェルは、MuJoCo の初期 roll と pitch と yaw と高さを指定する
  - 試行シェルは、歩行計画を起動せずに復帰要求を送る
  - 試行シェルは、成功後だけ既存の立位または歩行起動を選べるようにする
- 記録では、開発者は既存の状態 CSV を変更せず、新しい復帰 CSV を作る
  - 新しい復帰 CSV は、復帰状態と姿勢分類と接触と指令関節角を含む
  - 記録は、初期姿勢と復帰時間と最大角速度と最大指令トルクと再試行回数を要約する
  - 映像は、胴体と脚と地面接触が同時に見える固定視点を使う
- 単体試験では、開発者は分類境界と補間と左右反転と時間切れを検証する
  - 分類試験は、正規化した quaternion と符号反転した同値 quaternion を同じ姿勢に判定する
  - 補間試験は、始点と終点と速度連続性と速度上限を検証する
  - 指令試験は、全関節の位置と速度とトルクの上限を検証する
- 結合試験では、開発者は新しい復帰ノードが復帰中に歩行指令を混ぜないことを検証する
  - 試験は、復帰中に古い `local_plan` と新しい `cmd_vel` を送っても復帰指令だけが出ることを確認する
  - 試験は、復帰失敗後に `SAFETY` の減衰指令が出ることを確認する
  - 試験は、`RECOVERY` の成功後にだけ `RESUME` へ移ることを確認する

### 結論

- 元の実装は歩行用制御器を起動時に選び、転倒復帰用の排他的な指令経路を持たない
- 新しい実装は既存ソースを変更せず、別ノードと remap で歩行用制御器との競合を防ぐ

## 第5章 段階的な試験計画

### 概要

- 開発者は、指定された仰向けと左右の横倒しの初期条件を固定して判定と復帰を作り、そのあと階段転倒で実際に現れた姿勢へ対応を広げる
- 開発者は、平地で再現性を確認してから、摩擦と初期角度と関節ずれを変える
- 開発者は、シミュレーションの合格後も実機を自動的な次段階とは扱わない

### 詳細

- 初期条件試験では、開発者は平地上の仰向けと左横倒しと右横倒しを MuJoCo に与える
  - 胴体位置は `x = 0` と `y = 0` に置き、yaw は零にする
  - 仰向けでは、胴体姿勢の roll を正の百八十度、pitch を零にして背中側を地面へ向ける
  - 左横倒しと右横倒しでは、胴体姿勢の roll を正負の九十度、pitch を零にする
  - roll の正負と実際に接地した側面の対応は、最初の姿勢記録で確認して固定する
  - 胴体高さはモデルを地面へ貫通させず、短い自由落下後に指定した背中側または側面が接地する高さにする
  - 十二関節は脚を胴体へ寄せた初期角にし、関節速度と胴体速度は零にする
  - シミュレーション開始後は一秒間を整定時間にし、その後の姿勢を復帰開始状態として記録する
  - 合格条件は、復帰処理が仰向けと左右の横倒しを一意に判定し、分類の往復を起こさないことにする
- 仰向け復帰試験では、開発者は仰向けから横倒しを経て低い四脚支持へ移す
  - 最初の合格条件は、仰向けから脱して横倒しへ安定して移ることにする
  - 次の合格条件は、横倒しから四脚を地面側へ入れて低い四脚支持へ移ることにする
  - うつ伏せへ移った場合だけ、復帰処理は腹部接地から低い四脚支持へ移る補助動作を使う
- 横倒し復帰試験では、開発者は左右の各側面から低い四脚支持へ移す
  - 左横倒しと右横倒しは、左右を反転した同じ状態遷移を使う
  - 合格条件は、左右の各初期姿勢から低い四脚支持へ移ることにする
- 押上げ試験では、開発者は `RECOVERY` が作った低い四脚支持から胴体の押上げを実行する
  - 低い四脚支持を独立したユーザー初期条件として生成しない
  - 合格条件は、転倒せずに所定の高さと姿勢へ達し、五秒以上保持することにする
- 階段転倒試験では、開発者は自然転倒後に観測された姿勢だけを追加対象にする
  - 横倒しで止まった場合は、左右の横倒しから低い四脚支持へ移す動作を検証する
  - うつ伏せで止まった場合は、腹部接地から低い四脚支持へ移す動作を検証する
  - 仰向けで止まった場合は、平地で作った仰向け復帰を階段上の接触条件で検証する
- 引渡し試験では、開発者は復帰完了後に既存の立位制御へ引き渡す
  - 合格条件は、引渡し時に指令関節角とゲインが不連続に跳ばないことにする
  - 合格条件は、立位を五秒保持したあと低速の `cmd_vel` で歩行を開始できることにする
- ロバスト性試験では、開発者は初期条件を行列として変える
  - 初期 roll と pitch は、基準角の前後へ小さいずれを加える
  - yaw は、地面に対して複数方向を使う
  - 地面摩擦は、低摩擦と基準摩擦と高摩擦を使う
  - 関節角は、基準初期角へ小さいずれを加える
  - 再現試行は、各条件で複数回を実行する
- 受入基準では、開発者は成功だけでなく安全上限も評価する
  - 成功率は、基準平地の各対象姿勢で事前に定めた割合以上にする
  - 復帰時間は、時間切れより十分短い分布にする
  - 最大関節速度と最大指令トルクは、復帰専用上限以内にする
  - 胴体と脚の衝突は、許可した接触部位以外で継続しないようにする
  - 失敗時は、ロボットが指令を出し続けず既存の `SAFETY` へ到達するようにする

### 結論

- 元の試行は立位から歩行を始めるため、転倒姿勢ごとの成功率と安全上限を測らない
- 新しい試行は姿勢別の段階試験と初期条件行列を使い、復帰可能範囲と失敗境界を記録する

## 第6章 実機へ進む条件

### 概要

- 実機評価は、自作の低レベル復帰と Unitree 公式の `RecoveryStand()` を別の候補として比較する
- 実機評価は、シミュレーション成功だけで開始せず、指令所有権と非常停止と試験設備を先に確認する

### 詳細

- 自作の低レベル復帰では、開発者はシミュレーションと同じ `LegCommandArray` を `rt/lowcmd` へ渡す
  - この候補は動作を変更しやすいが、接触衝撃と実機差を開発側が管理する必要がある
  - 最初の実機試験は、胴体を吊れる設備と広い空間と即時停止手段を前提にする
- Unitree 公式復帰では、開発者は `SportClient::RecoveryStand()` を専用の所有権切替経路から呼ぶ
  - この候補はメーカー実装を利用できるが、内部軌道と安全判定を本リポジトリから確認できない
  - 呼出し前には、開発者は低レベル指令を停止し、MotionSwitcher の状態を確認する
  - 完了後には、開発者は Sport モードを停止してから低レベル制御を再取得する
- 実機へ進む判定では、開発者は次の条件をすべて満たす
  - シミュレーションは、対象姿勢の基準条件とずらした条件で再現性を示す
  - 指令は、位置と速度とトルクの復帰専用上限を全試行で守る
  - 中断は、通信断と状態欠落と時間切れで確実に作動する
  - 所有権切替は、低レベル指令と Sport 指令を同時に出さない
  - 作業者は、メーカーの安全手順と試験設備を別途確認する

### 結論

- 元の実装は Unitree の低レベル指令を使うが、公式復帰 API を接続していない
- 実機候補は二つ存在するため、開発者は動作性能だけでなく指令所有権と検証可能性で採否を決める

## 第7章 実装順序と完了条件

### 概要

- 開発者は、小さい変更ごとに判定と制御と記録を完成させ、次の姿勢へ進む
- 最初の成果は MuJoCo 上の手動復帰に限定し、自動復帰と実機対応を後段へ置く

### 詳細

- Step 01では、開発者は平地上の仰向けと左右の横倒しの初期姿勢生成と姿勢分類器と CSV 記録を実装する
- Step 02では、開発者は `RECOVERY` と歩行指令を遮断する切替と `SAFETY` への失敗遷移を実装する
- Step 03では、開発者は仰向けから横倒しへ移るキーフレームを調整する
- Step 04では、開発者は横倒しから低い四脚支持へ移るキーフレームを調整する
- Step 05では、開発者は必要な場合だけうつ伏せから低い四脚支持へ移る補助動作を調整する
- Step 06では、開発者は共通終点から既存立位への引渡しを実装する
- Step 07では、開発者は初期条件行列を自動実行し、成功率と安全上限を集計する
- Step 08では、開発者は自動起動の必要性と誤検出対策を評価する
- Step 09では、開発者は Unitree 公式復帰と自作復帰を実機候補として比較する
- MuJoCo 版の完了条件では、開発者は次の結果を残す
  - 平地上の仰向けと左右の横倒しの初期状態を同じ条件で再実行できる
  - 仰向けと左右の横倒しから低い四脚支持を経て立位へ到達する
  - 階段転倒後に実際に観測された姿勢から立位へ到達する
  - 失敗試行は、上限時間内に既存の `SAFETY` へ移る
  - 復帰中の関節指令は、歩行用の関節指令と競合しない
  - 復帰後のロボットは、既存の低速歩行へ移れる
  - 記録は、初期姿勢と状態遷移と指令上限と成功理由または失敗理由を追跡できる

### 結論

- 最初に着手する実装は、MuJoCo 上の姿勢分類と手動起動の関節空間復帰にする
- 仰向け復帰が成立したあとも、実機対応は別の安全審査と所有権切替の実装を完了条件にする

## 第8章 走行中の転倒判定と自動モード切替

### 概要

- この章では、開発者は静止した寝姿勢だけでなく、走行中に転倒した状態を角度から検出する
- この章では、開発者は転倒候補を一定時間確認し、階段走行中の一時的な傾きを転倒と誤判定しないようにする
- この章では、新しい復帰ノードが歩行指令と復帰指令の所有者を一か所で切り替える
- この章では、第7章の手動復帰を初期確認に残し、その後へ自動復帰を追加する

### 詳細

- 転倒判定が使う値は、既存値と新規値に分ける
  - `body.pose.orientation`
    - 区分は、既存である
    - 目的は、胴体の quaternion を受け取ることである
    - 新しい復帰ノードは、この値を読み取るだけで変更しない
  - `body.pose.position.z`
    - 区分は、既存である
    - 目的は、胴体高さを受け取ることである
    - 新しい復帰ノードは、この値を読み取るだけで変更しない
  - `body.twist.angular`
    - 区分は、既存である
    - 目的は、胴体角速度を受け取ることである
    - 新しい復帰ノードは、この値を読み取るだけで変更しない
  - `joints.position` と `joints.velocity`
    - 区分は、既存である
    - 目的は、関節角と関節速度を受け取ることである
    - 新しい復帰ノードは、この値を読み取るだけで変更しない
  - `u`
    - 区分は、新規作成である
    - 目的は、胴体 z 軸の向きを一つの値で表すことである
    - 既存の quaternion から毎周期計算する
  - `fall_pending_time`
    - 区分は、新規作成である
    - 目的は、転倒候補が連続した時間を表すことである
  - `recovery_keyframe_index`
    - 区分は、新規作成である
    - 目的は、`RECOVERY` が現在追従している関節キーフレームを表すことである
  - `recovery_attempt_count`
    - 区分は、新規作成である
    - 目的は、一回の試行で実行した復帰回数を表すことである
  - `recovery_mode`
    - 区分は、新規作成である
    - 目的は、新しい復帰ノード内で `RECOVERY` と `RESUME` を切り替えることである
- 姿勢判定では、開発者は Euler 角だけでなく quaternion から求めた胴体座標の z 軸を主判定に使う
  - 判定値 `u` は、胴体座標の z 軸と世界座標の z 軸の内積にする
  - quaternion を `(qx, qy, qz, qw)` とすると、判定値は `u = 1 - 2 * (qx^2 + qy^2)` で求める
  - `u = 1` は胴体上面が上を向く姿勢を表し、`u = -1` は仰向けを表す
  - roll と pitch は記録と左右方向の説明に使い、百八十度付近の不連続を主判定へ持ち込まない
- 転倒候補では、開発者は角度と高さと角速度を組み合わせる
  - 初期の直立継続条件は `u >= 0.82` とし、胴体の傾きがおよそ三十五度以内である状態を表す
  - 初期の転倒候補条件は `u <= 0.57` とし、胴体の傾きがおよそ五十五度以上である状態を表す
  - うつ伏せは `u` だけでは直立と区別できないため、胴体高さが低い条件を併用する
  - 胴体角速度が大きい状態は、着地途中と静止した転倒を区別する補助条件に使う
  - 接触情報はシミュレーションと実機で意味が異なるため、初期実装では必須条件にしない
  - 数値は初期値として設定へ出し、Step 23 の正常な階段走行ログから誤判定しない範囲へ調整する
- 時間判定では、開発者は一回の標本で復帰へ切り替えない
  - 新規の `fall_pending_time` は、転倒候補条件が連続して成立した時間を計る
  - 初期の確定時間は 0.4 秒とし、階段の一段を上る短い pitch 変化を無視する
  - 直立継続条件へ戻った場合は、既存の `SIT` または `READY` を維持する
  - 高さが危険閾値を下回り続けた場合は、`u` が正でもうつ伏せまたは脚崩れとして転倒を確定する
- 姿勢分類では、開発者は復帰確定後に仰向けと横倒しとうつ伏せを分ける
  - `u` が負の仰向け閾値以下の場合は、仰向け用のキーフレームを選ぶ
  - `u` の絶対値が小さい場合は、左右の横倒し用のキーフレームを選ぶ
  - `u` が正で胴体高さが低い場合は、うつ伏せまたは脚崩れ用のキーフレームを選ぶ
  - 左右判定は quaternion から求めた胴体横軸の鉛直成分を使い、roll の符号だけに依存しない
- 自動モードでは、開発者は次の処理を順に接続する
  - 新しい復帰ノードは、既存の `SIT` と `READY` を変更せず転倒条件を監視する
  - 転倒条件が一定時間続いた場合は、新しい復帰ノードだけが `RECOVERY` へ移る
  - `RECOVERY` は、姿勢判定と復帰動作と立位確認を実行する
  - `RESUME` は、転倒前の計画を捨て、新しい計画を待って速度を段階的に戻す
  - `RECOVERY` が失敗した場合は、既存の `SAFETY` へ移る
- 指令の排他制御では、`robot_driver` が最終的な `LegCommandArray` の所有者を決める
  - 通常時は、新しい復帰ノードが既存の歩行関節指令をそのままモータ側へ渡す
  - `RECOVERY` では、復帰制御器だけがモータ指令を出す
  - `RESUME` では、新しい復帰ノードが立位指令から歩行関節指令へ段階的に切り替える
  - local planner が復帰中に計画を publish しても、新しい復帰ノードは歩行関節指令をモータ側へ渡さない
  - 新しい `recovery_mode` は、既存の `control/mode` と別に管理する
  - 復帰状態と失敗理由は専用の状態トピックへ publish し、試行シェルと記録器が同じ遷移を確認できるようにする

### 結論

- 元の実装は走行中の胴体角度を使って転倒を判定せず、歩行から復帰へ自動的に切り替えない
- 新しい判定は quaternion の胴体座標 z 軸と高さと継続時間を使い、正常な階段姿勢と転倒を分ける
- 新しいモード切替は歩行と復帰のモータ指令を同時に出さず、復帰中の NMPC 指令混入を防ぐ

## 第9章 復帰後の走行再開

### 概要

- この章では、開発者は復帰成功後に古い歩行計画を再利用せず、現在姿勢から local planner と NMPC を同期し直す
- この章では、開発者は上流から届き続ける新しい `cmd_vel` だけを使い、転倒前の古い速度指令を保存して再生しない
- この章では、開発者は速度を段階的に戻し、復帰直後の急な踏出しを防ぐ

### 詳細

- 復帰開始時では、復帰処理は local planner へ零速度状態を通知する
  - 新しい復帰ノードは、復帰中に local planner へ零の `cmd_vel` を出す
  - 新しい復帰ノードは、復帰中に出た `local_plan` を走行再開の有効計画として扱わない
  - 起動側は、転倒中も `cmd_vel` の送信元を止めず、最新の操作者要求を継続して publish できる
  - 新しい復帰ノードは、復帰中に届いた速度要求を local planner へ渡さない
- `RESUME` の計画再同期では、復帰後の現在姿勢から歩行計画を作り直す
  - 新しい復帰ノードは、復帰完了後に零の `cmd_vel` を local planner へ送り続ける
  - 新しい復帰ノードは、復帰完了時刻より新しい stamp を持つ `local_plan` だけを走行再開の判定に使う
  - 新しい復帰ノードは、新しい有効計画が連続して届くまで自分の立位 PD 指令をモータ側へ出す
  - local planner と NMPC の内部状態は変更しない
  - 新しい計画が成立しない場合は、走行へ戻さず立位 PD を維持する
- `RESUME` の速度復帰では、復帰直後の急な踏出しを防ぎながら走行を再開する
  - 最新の `cmd_vel` を零から目標値へ滑らかに戻す
  - 速度倍率は初期値を零にし、二秒程度を初期値として一まで増やす
  - ramp 中に roll または pitch が再び転倒候補へ入った場合は、復帰処理が速度倍率を零へ戻す
  - 新しい `cmd_vel` が途切れた場合は、復帰処理が古い指令を再生せず立位を維持する
  - 復帰完了後に操作者が停止を指令した場合は、復帰処理が走行を再開しない
- 再転倒では、開発者は無限に復帰と走行を繰り返さない
  - 一回の試行で許す自動復帰回数は、初期値を二回にする
  - 同じ場所で短時間に再転倒した場合は、復帰処理が走行再開を禁止する
  - 上限へ達した場合は、復帰処理が既存の `SAFETY` へ移り、零速度と減衰制御を維持する
  - 階段形状そのものが現在の歩行能力を超える場合は、復帰機能が階段通過能力を代替しない

### 結論

- 元の実装は転倒前後の計画を区別せず、復帰後に歩容位相と NMPC 初期状態を同期し直す経路を持たない
- 新しい引渡しは復帰後の新しい計画だけを受理し、最新の速度要求を ramp して走行を再開する
- 同じ障害で再転倒する場合は、復帰処理が回数を制限して安全停止する

## 第10章 二つの復帰シナリオ

### 概要

- シナリオ1では、開発者はロボットを初期状態から寝かせ、角度判定が自動復帰を開始してから平地走行へ移ることを確認する
- シナリオ2では、開発者は既知の失敗階段を走行させ、転倒検出と復帰と計画再同期と走行再開を一つの試行で確認する
- 二つのシナリオは同じ復帰手順と同じ復帰制御器を使い、起動時だけの特別な復帰経路を作らない

### 詳細

- シナリオ1の初期状態では、試行シェルは MuJoCo の `init_pose` へ寝姿勢を設定する
  - 寝姿勢は仰向けと左横倒しと右横倒しの三種類にし、うつ伏せをシナリオ1の初期状態にしない
  - 仰向けの roll は正の百八十度にする
  - 左右の横倒しの roll は正負の九十度にする
  - 三種類とも pitch と yaw は零にする
  - 関節角と胴体高さと整定時間は第5章の初期条件試験と同じ値を使う
  - local planner と速度指令は起動してもよいが、復帰処理は復帰完了まで歩行指令を遮断する
  - 復帰処理は、最初の状態受信後に転倒条件の継続を確認して自動復帰へ入る
  - 復帰成功後は、`RESUME` が計画再同期と速度復帰を実行して低速の平地走行を始める
  - 合格条件は、三種類の各初期姿勢から手動の `control/mode` 切替を使わずに立位へ到達し、その後に二メートル以上を転倒せず進むことにする
- シナリオ1の記録では、記録器は起動直後から全状態を保存する
  - CSV は、`u` と roll と pitch と胴体高さと角速度と復帰状態とモード所有者を含む
  - CSV は、転倒確定時刻と復帰開始時刻と立位確認時刻と最初の新規計画時刻と走行再開時刻を含む
  - 映像は、寝姿勢から立位と最初の歩行までを連続して含む
- シナリオ2の地形では、試行シェルは Step 23 で完走できなかった高さ 0.15 m と踏面 0.30 m の上り四段と下り四段を使う
  - 最初の段階では、開発者は既存設定の `jp_stair_matrix_h15_d30_n04.xml` と低速指令を使う
  - 試行は、転倒を人工的な角度変更で作らず、既存の階段失敗から復帰処理を始動する
  - 復帰動作は、転倒位置の地形を平地へ置き換えず、段差上の実際の接触条件で実行する
  - 段端で脚を展開できない場合は、記録器が地形による復帰失敗として区別する
- シナリオ2の段階試験では、開発者は走行再開の故障箇所を分けて確認する
  - 段階Aでは、開発者は階段走行ログを再生せず shadow 判定だけを動かし、転倒時刻と誤判定を確認する
  - 段階Bでは、開発者は転倒検出後に `RECOVERY` へ移り、歩行指令が遮断されることを確認する
  - 段階Cでは、開発者は階段上で復帰動作を実行し、立位確認までを評価する
  - 段階Dでは、開発者は新しい計画の受理と速度 ramp を有効にし、再び歩き始めることを確認する
  - 段階Eでは、開発者は残りの階段と退出区間まで走らせ、再転倒と安全停止を評価する
- シナリオ2の合格条件では、開発者は復帰と走行再開を別に判定する
  - 転倒検出は、胴体が地面へ落ちてから一秒以内に確定する
  - 復帰中は、古い `local_plan` が関節指令へ混入しない
  - 復帰成功は、直立角度と胴体高さと角速度が所定時間にわたり成立する
  - 走行再開は、復帰後に生成された新しい `local_plan` を使って一メートル以上進む
  - 最終目標は、復帰後に残りの階段と退出区間を完走する
  - 同じ障害で二回目の転倒が起きた場合は、復帰処理が停止して試行を失敗として残す
- 実装順序では、開発者は次の Step を追加する
  - Step R01では、開発者は `u` と高さと継続時間による shadow 転倒判定を追加する
  - Step R02では、開発者は歩行指令と復帰指令を切り替える処理と復帰状態トピックを追加する
  - Step R03では、開発者は初期寝姿勢からの姿勢別復帰を追加する
  - Step R04では、開発者は新しい復帰ノードへ新規計画 gate と速度 ramp を追加する
  - Step R05では、開発者はシナリオ1を姿勢別に反復して復帰と平地走行を確認する
  - Step R06では、開発者は既知の失敗階段で shadow 判定と指令遮断を確認する
  - Step R07では、開発者は階段上の復帰と走行再開を段階Cから段階Eまで確認する
  - Step R08では、開発者は初期角度と階段上の転倒位置を変えて成功率と失敗境界を集計する

### 結論

- シナリオ1は、仰向けと左右の横倒しでも走行時と同じ角度判定と復帰処理が動くことを確認する
- シナリオ2は、既知の階段転倒を起点に復帰し、新しい NMPC 計画へ同期して走行を再開できるかを確認する
- 復帰機能は失敗階段の通過性能を自動的に改善しないため、再転倒時は回数制限によって安全停止する
