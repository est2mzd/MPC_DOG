## 0. まず全体像:このロボットは何をしているのか

4本足のロボット(Go2)を歩かせたい。やることは大きく3つに分解できる。

1. **今どこにいて、どう動いているかを知る**(観測)
2. **次の一瞬(たとえば0.01秒後)、各足がどれくらいの力で地面を押せば、目標の速度で
   転ばずに歩けるかを計算する**(MPC = Model Predictive Control、モデル予測制御)
3. **その「力」を、実際にモーターへ送る「関節トルク」に変換する**(トルク変換)

これを1秒間に100回(`mpc_frequency=100`)繰り返す。

**なぜ「力」を直接最適化するのか(MPCの発想)**: 関節角度を直接決めるのではなく、
「胴体(centroid、重心)にどんな力・モーメントが働けば目標の動きになるか」を先に決め、
そのために各足がどれだけ地面を押すべきかを最適化する。これを**Centroidal(重心)/SRBD
(Single Rigid Body Dynamics、単剛体力学)モデル**と呼ぶ。胴体を1つの剛体とみなし、
4本足からの反力だけで運動が決まると簡略化することで、リアルタイムで解ける最適化問題になる。

**なぜ「予測」なのか(Predictiveの意味)**: 「今、この力を出したらどうなるか」だけでなく、
「これから0.5秒先まで、各足がいつ地面につくか(歩容=Gait)」を先読みし、その未来の接地計画を
考慮した上で、今この瞬間に出すべき力を決める。ただし実際に使うのは、計算した未来の計画のうち
**先頭の1ステップ分だけ**で、次の周期にまた同じ計算をやり直す。これを**Receding Horizon
(受け取っては捨てる、移動ホライズン)**と呼ぶ。

## 0.5. アーキテクチャ全体:この「頭脳」は2つの体のどちらにでも載せられる

**背景**: 上記1〜3の計算ロジック(制御の「頭脳」)そのものは、シミュレータで動かそうが
実機で動かそうが変わらない。しかし「頭脳」の外側 — センサーからどうやって観測を受け取るか、
計算したトルクをどうやって実際のモーターへ送るか(「体」の部分) — は、シミュレータと実機で
大きく異なる。`external/Quadruped-PyMPC`はこの2つを明確に分離して実装している。これが
v2で見落としていた点である。

**目的**: 「頭脳」(制御ロジックの核)と「体」(デプロイ形態)を区別して理解する。

### 頭脳(共通の核):3つのクラス

以下の3つのクラスが、以降のステップ3〜9で説明する処理のすべてであり、
**2つのデプロイ形態のどちらからも一字一句同じコードとして呼ばれる**(本パスで
`ros2/run_controller.py`199–204行と`simulation/simulation.py`134–139行を比較して確認)。

- `WBInterface`(`interfaces/wb_interface.py`) — 歩容・着地点・状態集約・トルク変換
- `SRBDControllerInterface`(`interfaces/srbd_controller_interface.py`) — MPC呼び出し
- `Centroidal_Model_Nominal` / `Acados_NMPC_Nominal`(`controllers/gradient/nominal/`) — 力学モデルとOCP

### 体その1: 単体プロセス版(`simulation/simulation.py::run_simulation`)

1つのPythonプロセスの中で「観測→頭脳→トルク→MuJoCo物理を1歩進める」を直接ループで
回す(v2のステップ1・10で説明した内容)。シミュレーションと制御が同じループ・同じ変数
空間の中にあるため、実装は単純だが、**実機には使えない**(実機のセンサー読み取りと
モーター指令は別のハードウェア層であり、Python 1プロセスの中で完結しない)。

**本リポジトリ(`mpc_dog`)のワークショップが使っているのはこちらだけである。**
`mpc_dog`自身のREADMEに「**非目標: 実機ROS2デプロイ**」と明記されている
(`/home/takuya/work/mpc_dog/README.md` 175行)。つまりROS2版を使わないのは意図的な
スコープ限定であり、ROS2版が存在しない・重要でないという意味ではない。

### 体その2: ROS2 2ノード版(`ros2/run_controller.py` + `ros2/run_simulator.py`)

実機デプロイを見据えた構成。「頭脳(計算)」と「体(センサー・モーター)」を
**別々のROS2ノード(≒別プロセス)**に分離し、ROS2トピック(メッセージのやり取りの
仕組み)経由で通信する。本パスで両ファイルを全文読み、次の構造を確認した。

```
┌─────────────────────────────┐        /base_state (BaseState)        ┌──────────────────────────────┐
│  Quadruped_PyMPC_Node        │ <───────────────────────────────────  │  Simulator_Node               │
│  (run_controller.py)         │        /blind_state (BlindState)      │  (run_simulator.py)           │
│  = 「頭脳」                    │ <───────────────────────────────────  │  = 「体」                       │
│                               │                                        │  (シミュレータ or 将来は実機の  │
│  WBInterface +                │        /control_signal (トルク)        │   低レベルドライバに置換可能)     │
│  SRBDControllerInterface を    │ ───────────────────────────────────>  │                               │
│  そのまま呼ぶ(頭脳は共通)        │                                        │  MuJoCoで物理を1歩進める、       │
│                               │        /trajectory_generator          │  トルクを適用、状態を測って       │
│  Joystickから速度指令(/joy)      │        (目標関節角度+PDゲイン)          │  publish、を繰り返す            │
└─────────────────────────────┘ ───────────────────────────────────>  └──────────────────────────────┘
```

**重要な発見(本パスで直接コードを読んで確認)**: `Quadruped_PyMPC_Node`は内部に
**独自のMuJoCoインスタンス**を持っているが、これは物理シミュレーションのためではない
(`run_controller.py`502–504行、`mujoco.mj_forward`を呼んでおり`mj_step`は呼んでいない)。
受信した実センサー値(関節角度・胴体姿勢など)をこのMuJoCoモデルへコピーし、
`mj_forward()`(物理を進めずに運動学だけ再計算する関数)を呼ぶことで、
「今の関節角度なら、足先はどこにあるか」「ヤコビアンは何か」「質量行列は何か」と
いった、頭脳(`WBInterface`)が必要とする幾何・力学量を**計算するためだけ**に
MuJoCoを流用している(衝突判定も無効化、503行`disableflags=16`)。つまりMuJoCoは
「シミュレータ」としてだけでなく「リアルタイム運動学計算エンジン」としても
使われている。実機に繋いだ場合、この仕組みによってコード変更なしに実際の
センサー値からヤコビアン等を計算できる。

**もう1つの重要な発見**: `Quadruped_PyMPC_Node`は計算したトルクを2種類のメッセージで
publishしている。
- `/control_signal`(`ControlSignal`メッセージ): 立脚脚の`τ=-JᵀF`から来た生トルク
- `/trajectory_generator`(`TrajectoryGenerator`メッセージ): 遊脚の目標関節角度・角速度
  +PDゲイン(`kp`, `kd`)

これは実機ロボットの低レベルコントローラ(モーター直近のファームウェア、
`dls2_interface`経由、本パスでは未読)が、遊脚は「目標角度に対するPD制御」、
立脚は「指定されたトルクをそのまま出力」という**2種類の指令**を使い分けられるように
設計されているためだと考えられる(**解釈**、低レベルコントローラ側のコードは
このリポジトリに無いため未確認)。`run_simulator.py`(シミュレータ版の「体」)は
`/control_signal`のトルクだけを実際に使い、`/trajectory_generator`は受信して
保存するだけで使っていない(141–144行、`desired_joints_position`はどこにも
参照されない)。つまりシミュレータ版の「体」はPD側を実装していない。

**なぜ2ノードに分かれているのか(設計上の必然性)**: 実機では「制御の計算」と
「センサー読み取り・モーター駆動」は物理的に別のハードウェア・別のリアルタイム制約を
持つ(モーター駆動は数百Hz〜kHzで待ったなしだが、MPCの計算は100Hz程度で間に合えばよい)。
`run_controller.py`が内部で持つ複数の並列化戦略(スレッド、`multiprocessing.Queue`、
共有メモリ+seqlock)は、まさに「MPCの計算(遅くてもよい)」と「WBC/トルク出力
(速くないといけない)」を別の実行単位に分離するための実装であり(78–124行、
279–410行)、単体プロセス版の`simulation.py`には存在しない関心事である。

**この節を読む理由**: ステップ3〜9で説明する`WBInterface`/`SRBDControllerInterface`が
なぜ「シミュレーション用の関数」ではなく「独立したクラス」として設計されているのかは、
このROS2版から2度目に(まったく同じ形で)呼ばれることを前提にしているためだと理解できる。
アーキテクチャを先に知らずにステップ5・8・9を読むと、クラス設計の意図(=デプロイ形態を
問わず使い回せる核にする)を見落とす。

## ステップ1: 今の状態を測る(2つの実装がある)

**背景**: 制御則がどんなに賢くても、今のロボットの位置・速度・関節角度が分からなければ
何も計算できない。**この「観測」の取り方が、単体プロセス版とROS2版で異なる**唯一無二の
差分ポイントである(取れる値の種類と意味は同じだが、取得元が違う)。

**目的**: 制御周期1回分の「観測」をすべて集める。

- **単体プロセス版**(`simulation/simulation.py::run_simulation`、173–205行): MuJoCoの
  シミュレーション状態(`env.mjData`)から**直接**、Python関数呼び出しで読み取る。
- **ROS2版**(`ros2/run_controller.py::Quadruped_PyMPC_Node`): `/base_state`
  トピック(`get_base_state_callback`、412–433行)と`/blind_state`トピック
  (`get_blind_state_callback`、437–447行)を購読(subscribe)し、メッセージが届くたびに
  内部変数を更新する。届いた値は上述の「内部MuJoCo(運動学計算専用)」へコピーされ、
  `mj_forward()`でヤコビアン等の追加量が計算される(494–545行)。
- **Input**(共通の意味): 4本の足の位置・速度、胴体の位置・速度・向き・角速度、
  重心位置、目標速度、各関節の角度・角速度、脚のヤコビアン。
- **Output**(共通の意味): 上記すべてが、次のステップ(`WBInterface.update_state_and_reference`)
  への引数として渡される。渡し方(直接の関数呼び出しか、コールバック内での呼び出しか)は
  違うが、**渡される中身とその後の処理(ステップ2〜9)は完全に同じ**。

**初心者がつまずきやすい点**: 「速度」や「位置」が world座標系(地面に固定)なのか
base座標系(ロボットの胴体に固定)なのかが変数ごとに違う。ROS2版では加えて、
DLS2メッセージの四元数の並び順(`[x,y,z,w]`)とMuJoCoの並び順(`[w,x,y,z]`)が違うため、
`np.roll(...,-1)`のような並び替えが必要になる(`run_controller.py`428行、
`run_simulator.py`136行)。座標系だけでなく、通信規格ごとのデータレイアウトの違いにも
注意が必要、というのがROS2版特有の学びである。

## ステップ3: いつどの足を地面につけるか決める `helpers/periodic_gait_generator.py`

**背景**: 4本足の動物・ロボットは、4本すべてを同時に浮かせることはできない(倒れる)。
「どの足をいつ地面につけるか」というスケジュール(歩容、Gait)を、力の最適化とは別に
先に決めておく必要がある。トロット(対角の2本ずつ交互)、ペース(左右2本ずつ交互)などの
パターンがある。この処理は`WBInterface`の内部から呼ばれるので、デプロイ形態(単体/ROS2)に
かかわらず同じコードが動く。

**目的**: 「今から先の時間、各足が接地しているかどうか」という0/1の時系列
(`contact_sequence`)を作る。

- **Input**: 各足の「位相」(0〜1で表した、1歩の周期の中の今どこにいるか)、
  歩行周波数(`step_freq`、既定1.35 Hz)、duty factor(1周期のうち何割接地しているか、
  既定0.74)。
- **Process**: 各足の位相を`位相 += dt × step_freq`で進め、位相が`duty_factor`未満なら
  接地(1)、それ以上なら遊脚(0)と判定する。この「位相を進める→判定する」処理を、
  今の位相を保存してから何十ステップも先読みし、最後に元の位相へ戻す、という形で
  「未来の接地スケジュール」を作る(副作用なしの先読み)。
  トロットでは4本足の位相にあらかじめ`[0.5, 1.0, 1.0, 0.5]`のズレ(offset)を与えることで、
  対角の2本が同時に接地・浮遊するパターンを作る。
- **Output**: `contact_sequence`(4本足 × ホライズン長の0/1配列)。この配列の**1列目
  (今この瞬間)**が`current_contact`として使われ、それ以外の列(未来)がステップ6・7の
  MPCの中で「未来のどの時点でどの足が使えるか」の材料になる。

**次のステップとのつながり**: この`contact_sequence`は、ステップ6の運動方程式の中で
「決定変数」ではなく「外から与えられた既知の値(パラメータ)」として使われる。この
役割分担を先に理解しておくことが、ステップ6を正しく読むための鍵になる。

## ステップ4: どこに足を下ろすか決める `helpers/foothold_reference_generator.py`

**背景**: 「いつ」足を下ろすかはステップ3で決まった。次は「どこに」下ろすかを決める必要が
ある。これを直感的な公式(Raibertヒューリスティックと呼ばれる、1980年代からある古典的な
考え方)で計算する。MPCの最適化とは別の、比較的単純な幾何計算。

**目的**: 各足の「着地目標位置」(`ref_feet_pos`)を計算する。

- **Input**: 胴体の位置・向き、現在の速度、目標速度、股関節(hip)の位置。
- **Process**: 直感的には「今の股関節の真下」を基準にして、
  1. 目標速度が速いほど、足を大きく前(または後ろ)にずらす
     (「半歩分だけ、速度に比例してずらす」という発想)
  2. 実際の速度が目標速度から遅れている/進みすぎている分を、追加で補正する
  3. 左右方向には、股関節から少し外側(`hip_offset=0.1m`固定)にずらして、
     足同士がぶつからないようにする
- **Output**: `ref_feet_pos`(4本足それぞれの、world座標系での目標着地位置)。この値は
  ステップ5で`ref_state`辞書に格納され、ステップ7のMPCのコスト関数の「参照値」
  (=これに近づけたい目標)として使われる。

**このステップがステップ3の後にある理由**: 「いつ地面から離れたか(lift-off)」
「いつ地面についたか(touch-down)」を検出するには、ステップ3の`current_contact`
(今の接地状態)と、1つ前の周期の接地状態(`previous_contact`)を比較する必要があるため。

## ステップ5: 全部の情報を1つにまとめる `interfaces/wb_interface.py::update_state_and_reference`

**背景**: ここまでのステップ1(観測)・3(歩容)・4(着地目標)はそれぞれ別の場所で
別の形式のデータを作ってきた。MPC(ステップ6・7)はこれらを1つの決まった形式
(辞書)として受け取りたい。この変換・集約をやるのがこの関数。「頭脳」の入口であり、
**単体プロセス版でもROS2版でも、この関数から先はまったく同じコードパスを通る**
(0.5節で確認済み)。

**目的**: ステップ6・7が直接使う3点セット、`state_current`(今の状態)・`ref_state`
(目標の状態)・`contact_sequence`(接地スケジュール)を組み立てる。

- **Input**: ステップ1の観測一式、ステップ3の`contact_sequence`、ステップ4の`ref_feet_pos`。
- **Process**:
  - ステップ3(`self.pgg.run(...)`)とステップ4
    (`self.frg.compute_footholds_reference(...)`)をこの関数の中から呼び出す。
  - 今の状態を`state_current`という辞書にまとめる。ここで**要注意な点**が2つある:
    - `position`には胴体位置ではなく**重心(CoM)位置**が入る
    - `linear_velocity`には重心速度ではなく**胴体(base)の速度**が入る
    - つまり「位置」と「速度」で基準点が違う、という非対称性がある
  - 目標状態を`ref_state`という辞書にまとめる。地形の傾き(roll/pitch)を推定し、
    目標速度をその傾きに合わせて回転させる補正も入る。
- **Output**: `state_current`, `ref_state`, `contact_sequence`。これらがそのまま
  ステップ6・7へ渡される。

**このステップを飛ばして次に進んではいけない理由**: ステップ6・7を読んでいて
「`position`ってCoM?胴体?」と迷ったら、答えは必ずここにある。

## ステップ6: 物理モデルを作る `controllers/gradient/nominal/centroidal_model_nominal.py`

**背景**: MPCが「未来を予測」するには、「今こういう力を出したら、次の瞬間どうなるか」を
表す数式(運動方程式)が要る。4本足のロボット全体を関節レベルで正確にモデル化すると
計算が重すぎて実時間では解けないので、「胴体を1つの剛体とみなし、4本の足からの
反力だけが作用する」という単純化(Centroidal/SRBDモデル)を使う。

**目的**: CasADi(数式を記号のまま扱うライブラリ)で「状態が今こうで、こういう力を
加えたら、次の瞬間の状態はこうなる」という関数を定義する。

- **Input(状態、30個の数値)**: 重心位置(3)・重心速度(3)・姿勢角roll/pitch/yaw(3)・
  角速度(3)・4本足の位置(3×4=12)・積分項(6)。
- **Input(入力、24個の数値)**: 4本足それぞれの速度(3×4=12、遊脚のときだけ意味を持つ)と
  4本足それぞれが地面を押す力(GRF, Ground Reaction Force、3×4=12)。**MPCが最終的に
  決めたいのはこの「力」の部分**である。
- **Input(パラメータ、29個の数値)**: 各足が接地しているかどうか(0/1、ステップ3の
  `contact_sequence`から)、摩擦係数、慣性行列、質量など。パラメータは「状態」や
  「入力」と違い、**最適化の対象ではなく、外から与えられて固定される値**。
- **Process(運動方程式、物理の中身)**:
  - 並進運動: 「重心の加速度 = (各足の力 × その足が接地しているか) の合計 ÷ 質量 + 重力」。
  - 回転運動: 「角加速度 = 慣性行列の逆行列 × (各足の力が重心まわりに作るモーメントの合計
    − 角速度に起因する慣性項)」という、剛体の回転の基本法則(オイラーの運動方程式)。
  - 足の位置: 接地中の足は「動かない」という前提(速度を強制的に0にする)。遊脚中の足だけ、
    実際の足速度がそのまま使われる。
  - 積分項: 定常偏差を抑える(PID制御でいう「I項」に相当する役割)。
- **Output**: `forward_dynamics()`という、状態・入力・パラメータを受け取って
  「次の瞬間の状態変化率」を返すCasADi関数。これがそのままステップ7のacados
  (数値最適化ソルバー)に渡される。

**初心者向けの一言**: 「状態」はMPCが予測する対象、「入力」はMPCが決める対象
(=最終的に欲しい答え)、「パラメータ」はMPCの外(歩容・地形・ロボットの物性値)から
すでに決まって渡されてくる値、と覚えるとよい。

## ステップ7: 最適な力を計算する `controllers/gradient/nominal/centroidal_nmpc_nominal.py`

**背景**: ステップ6で「物理法則」は用意できた。あとは「どんな力を出せば一番良いか」を
決める必要がある。「一番良い」を数式にしたものが**コスト関数**、「絶対に守らないといけない
条件」を数式にしたものが**制約**である。

**目的**: 「目標の速度・姿勢にできるだけ近づきつつ、無理な力を出さず、地面から
足が滑ったり浮いたりしない」という条件のもとで、最も良い力の時系列を計算する。

- **Input**: ステップ5の`state_current`/`ref_state`、ステップ6の運動方程式、
  ステップ3の`contact_sequence`。
- **Process**:
  - **コスト関数**: 実際の重みを見ると、重心のx,y位置のずれには**重みが0**(気にしない)、
    z位置(高さ)には強い重み、roll/pitch角のずれには強い重み、yaw角には**重みが0**
    (気にしない)。つまりこのMPCは「胴体の高さと傾きは厳密に保つが、水平位置と向き
    (yaw)は速度さえ合っていれば多少ずれてもよい」という設計思想になっている。
  - **摩擦の制約**: 「足が地面を押す力」が摩擦円錐に収まっているかを、4本足×5本の
    不等式(合計20本)で表現する。
  - **求解**: acados(専用の高速ソルバー)で解く。SQP、SQP_RTI(リアルタイム反復、
    実機向けに速い)、DDPなどのアルゴリズムを切り替えられる。
- **Output**: 予測ホライズン全体(たとえば0.5秒先まで)にわたる、状態と力の時系列。
  ただし実際に使うのは、この中の**一番最初の1ステップ分の力**だけ。

**初心者向けの一言**: 「コスト関数の重みが0の項目=そこは自由に動いてよい、という
設計判断」と読み替えると、パラメータの意味が理解しやすい。

## ステップ8: 「今使う分」だけを取り出す `interfaces/srbd_controller_interface.py`

**背景**: ステップ7のMPCは「未来何十ステップ分」の答えをまとめて返してくる。しかし
実際にロボットへ送るべき指令は「今この瞬間」の1つだけである(Receding Horizonの考え方)。
また、念のためもう一段「今、接地していない足の力は強制的にゼロにする」という安全策も入っている。

**目的**: MPCの答えから「今使う1ステップ分の力」を取り出し、遊脚の力を確実にゼロにする。

- **Input**: ステップ7のMPCが返す力の時系列(先頭ステップ分)、ステップ3の
  `current_contact`。
- **Process**: 先頭ステップ分の力(4本足×3成分=12個の数値)を取り出し、
  「その足が今接地していなければ、力に0を掛ける」という掛け算を行う。
- **Output**: `nmpc_GRFs`(4本足それぞれの、今使うべき地面反力)。ステップ9へ渡される。

## ステップ9: 力を関節トルクに変換する `interfaces/wb_interface.py::compute_stance_and_swing_torque`

**背景**: ステップ8までで「各足が地面を押すべき力」が決まった。しかしモーターが
実際に受け取れる指令は「関節トルク」(回転力)である。「足先に働く力」から「関節の
トルク」への変換が必要になる。地面についていない足(遊脚中)は代わりに「次に着地する
場所へ向けて足を振り出す」ための、別の制御(軌道追従)が必要になる。

**目的**: 立脚中の足には力をトルクに変換する計算を、遊脚中の足には振り出し軌道を
追従させる計算を、それぞれ適用して最終的な関節トルクを得る。

- **Input**: ステップ8の`nmpc_GRFs`、目標着地点、脚のヤコビアン、現在の関節角度・角速度。
- **Process**:
  - **立脚中の足**: 「関節トルク = −(ヤコビアンの転置) × 地面反力」という式で変換する
    (仮想仕事の原理)。追加のPD項は**無い**(このコード上の事実)。
  - **遊脚中の足**: 「離陸した場所」から「目標着地点」まで、滑らかな軌道
    (スイング軌道)を作り、その軌道に対してPD制御で足を動かすためのトルクを計算する。
  - 摩擦補償: 設定によっては、関節の摩擦力を打ち消す項を全部の足に追加する。
  - 安全のためのクリップ: 目標関節角度・速度が、現在の値から大きく離れすぎないように
    上限を設ける。
- **Output**: `tau`(4本足×3関節=12個の関節トルク、立脚分)と、遊脚の目標角度・角速度・
  PDゲイン。**ここで単体プロセス版とROS2版の出口が分かれる**(次のステップ10参照)。

**初心者がつまずきやすい点**: 立脚と遊脚で、まったく異なる2つの制御則が
1本のコードの中で`if`文によって切り替わっている。

## ステップ10: モーターを動かす(2つの実装がある)

**背景**: 計算した関節トルクを、実際に送らなければ何も起こらない。ここが「頭脳の計算」と
「実際にロボットが動く」をつなぐ最後の場所であり、ステップ1と対になって
**単体プロセス版とROS2版で実装が分かれる**もう一方のポイントである。

**目的**: トルクを安全な範囲に収めてから実際に送り、次の周期の観測につなげる。

- **単体プロセス版**(`simulation/simulation.py`237–251行): `tau`をモーター最大トルクの
  90%でクリップし、`env.step(action)`でMuJoCo物理を1ステップ直接進める。**次の周期の
  ステップ1へ、同じプロセス内でそのままループが戻る**。
- **ROS2版**(`ros2/run_controller.py`680–711行): `tau`を同様にクリップした後、
  `/control_signal`トピック(立脚トルク)と`/trajectory_generator`トピック(遊脚の
  目標角度・角速度・PDゲイン)の**2つのメッセージとしてpublishするだけ**。実際に
  モーターを動かす・物理を進めるのは、この関数の中では起きない。それを行うのは
  受信側の`Simulator_Node`(シミュレータ)、または実機の低レベルドライバである。
  `Simulator_Node`側(`run_simulator.py`121–150行)は、受け取ったトルクで
  `env.step()`を呼んで物理を1歩進め、新しい状態を`/base_state`・`/blind_state`として
  publishし返す。これが`Quadruped_PyMPC_Node`のステップ1(コールバック)を再び起動する。

**このステップが示す本質**: 単体プロセス版は「計算→即座に物理を進める」が1つの関数
呼び出しで閉じているが、ROS2版は「計算→publish」と「subscribe→物理を進める→publish」が
**別プロセス・別タイミングで非同期に**閉じる。ループが閉じる場所(1つの関数の中か、
2つのノードをまたぐネットワーク越しか)が違うだけで、閉じるという構造そのものは同じ。

**全体を振り返って**: ステップ1〜10を1周すると、「観測→歩容計画→着地点計画→
状態集約→物理モデル→最適化→取り出し→トルク変換→実行」という一連の処理が完了し、
再びステップ1に戻る。単体プロセス版はこれを1つのPythonループとして、ROS2版はこれを
2つのノード間のメッセージ往復として実現している、という違いだけである。
