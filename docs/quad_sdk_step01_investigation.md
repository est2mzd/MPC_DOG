### フェーズ3: 歩行成功、しかし再現性に課題

  (実測で起動開始から約20秒前後、試行ごとに変動)より短く、STAND送信が

### フェーズ5: 10m規模試験で新たな問題(ワールドサイズ・ワールド切り替え)が発覚(2026-08-30)

ユーザー承認を得て、joint_controller起動待ち修正後の初めての長時間試験
(0.3 m/s・cmd_vel指令40秒)を実施したところ、新たに2つの問題が見つかった。

- **試行G(`world:=flat.xml`のまま)**: t≈40〜45秒(x≈6.08〜6.80m)まで完全に
  安定して前進を継続(NMPC失敗0回)したが、その後`local_planner_node`が
  SIGABRTでクラッシュし、前進が停止した。地面ジオメトリを確認したところ、
  `flat.xml`の地面はx∈[-2.0, 7.0](全長9m)しかなく、ロボットが到達した
  停止位置(x=6.80m)は地面のx方向上限(7.0m)にほぼ一致していた。ユーザーの
  目視観察(「平面が小さすぎる、犬が落ちた」)とも整合し、**地面が10m規模の
  試験に対して狭すぎることが原因と判断した**。
- **試行H(`world:=big_flat.xml`に変更)**: 既存のより広いワールド
  (ビルド済み、22m×22mのメッシュ)へ変更して再試験したところ、
  **flat.xmlの時より明確に悪化した**(NMPC失敗54回、トルク閾値超過3198回)。
  ユーザーの目視観察(「直立後、少しジャンプ、その後低い姿勢で、不安定に歩いて、
  橋から落ちた」)と一致する具体的な数値パターン(t=13〜17秒でロボットが
  静止したままz異常上昇→急落、以降y方向ドリフトの蓄積、最終的にz=-30.2mへ
  物理破綻)をCSVで確認した。`big_flat.stl`を直接パースして地形メッシュの
  境界を確認した結果、x∈[0,22],y∈[0,22],z∈[0,0.1]とほぼ完全に平坦で、
  ロボットの到達範囲は十分内側に収まっていた。**「地面が狭くて端から落ちた」
  という仮説は、地形メッシュ自体の物理的境界という意味では否定された。**
  ワールド切り替えに伴う別の要因(地形マップ生成ノードの`terrain_mesh`解決、
  座標系オフセットの不整合等)が疑われるが未確認(進捗ログ2026-08-30 16:20参照)。

### 現在地: 成功条件(0.3 m/s・10m以上前進)を達成

**再現性問題(短時間・数m規模での「歩く/転倒がばらつく」問題)の根本原因は、
MUMPSの数値精度ではなく、起動シーケンス(コントローラ起動待ちが固定秒数で
不十分だったこと)だったと結論づけている。** MUMPSの精度起因を示す証拠は
調査全体を通じて一度も見つからなかった。CoinHSL導入・MA27変更・MPCゲイン
調整は現時点で不要と考えられる。

10m規模の長距離試験では、地面の狭さ(`flat.xml`は9m弱で端に達する)と、
より広い`big_flat.xml`(詳細メッシュ地形)への切り替えで生じる別の不安定性
(録画映像で地面からの落下を確認、原因はメッシュ衝突判定の脆さと推測、未確定)
という2つの問題が新たに見つかった。**flat.xmlと同じ単純なboxプリミティブ
地面のままサイズだけを拡大した`flat_wide.xml`を新規作成したところ、
walk_dist_x_m=10.078m(0.3 m/s、転倒なし)を達成し、目的で定めた成功条件を
初めて満たした(進捗ログ2026-08-30 17:00参照)。** これにより、10m規模の
不安定性は「地面が大きいこと自体」ではなく「big_flat.xmlの詳細メッシュ地形
特有の問題」だったと結論づけている。

## 試行錯誤の経緯

### 試行1: `reference`未指定(既定値)で実行

`quad_plan.py`を引数無しで起動 → 既定`robot_configs`は`"reference": "gbpl"`
(グローバルプランナからの目標地点待ち)。cmd_velを送っても無視され、ロボットは
完全に静止(base位置・速度がほぼ0、接触・GRFも常に0)したままだった。

**原因(事実、ソース確認済み)**: `quad_utils/launch/planning.py:209`
`'local_planner.use_twist_input': ref == 'twist'` — `reference`が`'twist'`
でない限りcmd_velは無視される。

**対応**: `robot_configs`に明示的に`"reference": "twist"`を指定。

### 試行2: `reference:="twist"`で再実行

静止はしなくなったが、`local_planner`のNMPCソルブが記録全体を通じて
**3924回連続失敗**(`NMPC solving fail`警告)。

`terrain_.isEmpty()`によるブロック(`local_planner.cpp:487`の
`"did not recieve the expected inputs"`警告)は一度も出ておらず、terrain_map
未受信が原因という仮説は**否定**した(ログで確認済み)。IPOPTの具体的な失敗理由
(Restoration_Failed等)はログの詳細度不足で特定できていない。

この時点でCoinHSL未導入が引き続き有力候補として残っている(未確定)。

### 試行2の副次的に見つけたスクリプトのバグ(修正済み)

- `quadsdk_step01_baseline.py`: CSV1行目(GRF未受信)を基準に`fieldnames`を決めていたため、
  後続行でGRF列が増えて`ValueError: dict contains fields not in fieldnames`でクラッシュ。
  → 全行で`contact_*`/`grf_*`列を既定値(False/0.0)で必ず埋めるよう修正。
- `.sh`: `set -e`下で記録ノードが例外落ちすると`wait`が失敗し、**後片付け(kill)に
  到達せずmujoco/plannerプロセスが残り続ける**バグ。→ `trap cleanup EXIT`化。
- `quadsdk_step01_baseline.py`: `use_sim_time`をノードに設定していたが、`/clock`購読
  タイミング次第で`get_clock().now()`が0から実際のsim時刻へ不連続にジャンプし、
  タイマー(記録時間)も巻き込まれて直後に発火する不具合(1行しか記録されない事象で発覚)。
  → `use_sim_time`設定を撤去し、`sim_time_s`は各メッセージの`header.stamp`から計算する
  方式に変更。タイマー自体は壁時計ベースのまま(記録時間の大まかな上限としてのみ使用)。

### 試行3: `control/mode`をWALK(2)へ切り替える(結果は次セクション参照)

公式tutorials(`tutorials/first-run/`)で判明した**未実施だった手順**:

```text
control/mode: 0=SAFETY(トルク0)、1=STAND(PD制御でノミナル姿勢)、2=WALK(local_plan追従)
```

これまでmode=1(STAND)しか送っておらず、**mode=2(WALK)を一度も送っていなかった**。
STANDのままだと、plannerがGRF/軌道を計算していても`robot_driver`はノミナル姿勢への
PD制御を続けるだけで、cmd_velを送っても歩かない可能性が高い。

`.sh`に`ros2 topic pub --once .../control/mode std_msgs/msg/UInt8 "data: 2"`を
quad_plan.py起動後・cmd_vel送信前に追加した。

**結果**: 次セクションの通り、これだけでは不十分だった(NMPC失敗が続いており、
根本原因は別に2つ残っていた)。

## 進捗ログ(2026-08-30 11:50時点)

### 試行3の結果: `control/mode`をWALK(2)へ切り替えても未解決

mode=2を追加して再実行 → 静止はしなくなったが、約14秒後に**完全に転倒(roll=-π、
仰向け)**。この間もNMPC解は4800回以上連続で失敗し続けていた(ログ確認できた最大値は
4852回)。mode切り替えだけでは
不十分と判明。

### 根本原因1(確定): `linear_solver`がハードコードで`"ma27"`(HSL)指定

`nmpc_controller.cpp:249`に`SetStringValue("linear_solver", "ma27")`があり、
CoinHSL未導入のこの環境では常に失敗する設定だった。ユーザー承認を得て
`"mumps"`(実際にビルドされているソルバー)へ変更。

**ここでハマった点**: `nmpc_controller`は静的ライブラリ(`libnmpc_controller.a`)として
`local_planner_node`にリンクされている。`colcon build --packages-select nmpc_controller`
だけでは`local_planner_node`の実行ファイルは再リンクされず(`--cmake-clean-cache`を
付けても、install先のファイルmtimeが更新されず古いバイナリのままに見えた)。
`strings`で実行ファイルの中身を直接確認して初めて気づいた。
`--packages-select nmpc_controller local_planner`の両方を指定して初めて反映された。

**結果**: 修正後、NMPC失敗が**0件**に。ロボットは接触を確立し(`contact_FL=True`継続)、
roll/pitchほぼゼロで安定して自立するようになった(以前は常に接触なし・転倒)。

### 根本原因2(確定): `cmd_vel_publisher_node`が起動直後に毎回クラッシュしていた

自立はしたが前進しない(x位置がほぼ不変)。切り分けのため`cmd_vel_publisher_node`を
単体で実行したところ、即座に例外で落ちていることが判明:

```text
terminate called after throwing an instance of
'rclcpp::exceptions::UninitializedStaticallyTypedParameterException'
what():  Statically typed parameter 'topics.cmd_vel' must be initialized.
[ros2run]: Aborted
```

原因: `.sh`が`cmd_vel_publisher_topics.yaml`(`topics.cmd_vel: cmd_vel`を宣言する
必須のparams-file)を渡していなかった。公式READMEのコマンド例には含まれていたが、
`.sh`作成時に見落としていた。**つまりこれまでの全試行でcmd_velは一度も配信されて
いなかった**。local_planner側は`last_cmd_vel_msg_time_max_`(既定2秒)を超えると
`cmd_vel_`をゼロにする実装のため、`is_stepping`が常にfalseになり、常にSTAND
(その場停止)モードのままだった。以前の「立つが歩かない」を完全に説明する。

`.sh`に`--params-file .../cmd_vel_publisher_topics.yaml`を追加。

**結果(後日判明)**: この修正は不十分だった。同yamlのノード名パターンが実際の
ノード名と一致しておらず(次の進捗ログ「試行4」参照)、最終的に`cmd_vel_publisher_node`
自体を生の`ros2 topic pub`へ置き換えることになった。

### その他の変更

- rviz2の既定起動を無効化(`quad_visualization.py`の`rviz`引数の既定値を
  `true`→`false`)。ヘッドレス記録では不要なため。ユーザー指示によりコメントで
  理由を明記し、コードの削除はしていない。
- 検証時間を45秒→**5秒**に短縮(ユーザー指示。1回の検証が長すぎて試行回数が
  稼げなかったため)。歩行の初動が確認できたら、10m以上を確認するために時間を
  伸ばす。

### 現状のまとめ(誤解しないよう明記)

- **まだ0.3 m/sで10m前進、という成功条件は達成していない。**
- 自立(転倒しない)ことは達成した。
- cmd_vel未配信という重大バグを直したばかりで、**その修正後の歩行検証はこれから**。

## 進捗ログ(2026-08-30 12:20時点)

### 試行4: `cmd_vel_publisher_node`が実は毎回クラッシュしていたことが判明

`.sh`が`cmd_vel_publisher_topics.yaml`を渡していなかったため`topics.cmd_vel`未初期化で
クラッシュ、修正のため`--params-file`で渡したが**それでもクラッシュ**(クラッシュ理由が
同じ)。原因は、そのyamlのノード名パターンが`/**/cmd_vel_publisher:`だが実際のノード名は
`cmd_vel_publisher_node`で**一致していなかった**(quad-sdk本体の設定ファイルの不整合)。
`--params-file`に頼らず、必要な全パラメータ(`topics.cmd_vel`, `update_rate`, `mode`,
`resample_sec`, `seed`, `test_duration`, `bounds.*`)を`-p`でインライン指定するよう変更。

さらに`cmd_vel_publisher.test_duration`がdouble型宣言なのに`DURATION_S=5`(小数点無し)を
渡すと整数型と解釈されクラッシュ(`InvalidParameterTypeException`)。`printf '%.3f'`で
明示的にfloat化するよう修正(`FORWARD_VEL_MPS`も同様に修正)。

**結果**: クラッシュは解消し、cmd_vel_publisher_nodeは最後まで正常に動作するように
なった。ただし依然として前進しない(walk_dist_x_m ≈ 0)。

### 試行5: トピック配線自体を直接検証(cmd_vel_publisher_nodeを経由せず生のros2 topic pubで確認)

`ros2 topic info --verbose`で確認:

- `/robot_1/local_plan`: `local_planner`が20Hz程度でpublish、`robot_driver`が正しく
  subscribe。トピック配線自体は正常。
- `/robot_1/cmd_vel`: `local_planner`が正しくsubscribe。配線は正常。

**しかし`/robot_1/local_plan`の中身を直接確認したところ**、26ステップのホライズン全体で
`twist.linear.x`が±0.006 m/s程度(ほぼゼロ)のまま。0.3 m/sを指令してもcmd_velが
**参照軌道の生成に反映されていない**ことを確認した(トピック配線は正しいのに、
中身が反映されない、という新しい切り分け結果)。

### 現状のまとめ(誤解しないよう明記)

- **まだ0.3 m/sで10m前進、という成功条件は達成していない。**
- 自立(転倒しない)は達成、cmd_velのトピック配線も正常、しかし**cmd_velの値が
  local_plannerの参照軌道計算に反映されていない**ことが新たな障害点として判明。
- 次の調査対象: `local_planner.cpp`の`getReference()`内、`use_twist_input_`が実際に
  trueとしてロードされているか、`cmd_vel_`変数が`is_stepping`判定やRaibert式歩幅計算へ
  実際に渡っているかを、ソース追跡またはデバッグ出力で確認する必要がある。

  **結果(後日判明)**: この方向の調査ではなく、次セクション(試行6)の通り
  `cmd_vel_publisher_node`自体を生の`ros2 topic pub`に置き換えることで解決した。
  `local_planner`側のロジックには問題が無く、原因は`cmd_vel_publisher_node`の

### 原因の特定(コード確認による事実)

現在使用しているワールド`flat.xml`(`external/quad-sdk/quad_simulator/quad_sim_scripts/
worlds/flat.xml.xacro`)の地面ジオメトリを確認したところ:

```xml
<geom name="floor" type="box" size="4.5 2 0.05" pos="2.5 0 -0.05" .../>
```

MuJoCoのbox `size`は半径(half-extent)のため、地面のx方向範囲は
`pos.x ± size.x` = `2.5 ± 4.5` = **x ∈ [-2.0, 7.0]**(全長9m)。
ロボットはx≈0付近から前進を始めるため、**歩ける有効距離は最大でも約7.0mしかない**。

試行Gでロボットが停止したx位置(6.80m)は、この地面のx方向上限(7.0m)に極めて近い。
**「local_planner_nodeのクラッシュ」も「歩行の停止」も、コントローラや解の問題ではなく、
ロボットが地面の端(x=7.0m)から落下し、有効な接地状態を失ったことが原因である
可能性が高い**(ユーザーの目視観察と、地面の範囲の数値、停止位置の数値が全て整合)。

**これはこれまでの「起動シーケンス」問題とは全く別のカテゴリの原因であり、
分類6(ソルバー失敗)や分類1(起動順序)ではなく、テスト条件そのもの
(ワールドのサイズがテスト距離要件(10m以上)を満たしていない)の問題である。**

`models/big_flat/meshes/big_flat.stl`、地面ジオメトリのpos指定`(-11,-11)`から

**このセッションを通じて「歩いた」「転倒した」と報告してきた結果の一部は、

### GIF目視検証で発生した問題と対応

一時停止後の再開で、ユーザーからGIFの見え方について複数回フィードバックを受け、
以下を順に対応した(全て`scripts/trial/make_gif.sh`の改善、`external/quad-sdk`は
無関係):

1. 「GIFで確認しているが歩いていない」→ 送っていたGIFが`camera_distance=20`
   (広角)や`10`(中間)で撮影されており、ユーザーの環境では見えづらかった
   可能性。
2. 「時刻が見えない」→ 時刻表示(`t=... / ...s`)を焼き込んだ最初の版は
   半透明白背景+黒文字だったため、ビューアによっては黒く潰れて見えていた
   可能性。不透明な黒背景+太字白文字・フォントサイズ拡大に変更。
3. 「時刻は見えるが小数点1桁に丸めてほしい」→ ffmpeg drawtextの`%{pts}`
   展開はデフォルトで小数点以下6桁固定のため、`%{eif:trunc(t):d}`と
   `%{eif:trunc(mod(t,1)*10):d}`を"."で連結する方式に変更し、1桁固定にした。
4. 「カメラが遠すぎる、初期の頃の位置がベスト」→ `quadsdk_step01_v0.1.gif`
   (旧・追従カメラ版)のズームを実測(`camera_distance`実質3.0m相当)し、
   固定カメラのままこの距離に一致させた。`run_quadsdk_step01_baseline.sh`の
   既定値も`10.0`→`3.0`に変更。
5. 「ファイル名が分からない」→ GIF左下にファイル名自体を焼き込むようにした。

各修正は、ffmpegで生成したGIFファイルを**Claude自身が`ffmpeg`でフレーム抽出
して目視確認してから**ユーザーへ送付する、という手順を徹底した(思い込みで
「直った」と報告しない)。
