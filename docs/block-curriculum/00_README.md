# 四足制御を、共通部分から積み上げる

このディレクトリは、四足コントローラを **Notebook 上で試行錯誤しながら** 積み上げるときの学習・実装の順番である。  
進め方の正本である。学習の本体はリポジトリ根の `notebook/` である。制御の計算はそこに書く。

---

## 1. 背景

このリポジトリ `mpc_dog` には、四足ロボットの制御スタックが2本ある。どちらも「人が出した胴体の速度」から「12関節のトルク」までを閉じたループで解く。置いてある場所は `external/` である。

| 略称 | 上流 | 性質 |
|---|---|---|
| **PyMPC** | `external/Quadruped-PyMPC` | Python。MuJoCo 上の Go2。重心まわりの短い予測最適化（acados）で接地力を決め、ヤコビ行列でトルクにする。状態推定はしない |
| **LC** | `external/legged_control` | C++ / ROS。Gazebo または実機。予測最適化（OCS2）のあとに、今この瞬間の全身 QP（WBC）でトルクを出す。線形カルマンフィルタがある |

理論の詳細は別ノートにある。

- PyMPC: [docs/qpympc-study/](../qpympc-study/00_README.md)
- LC: [docs/legged_control/](../legged_control/00_README.md)

やりたいことは、この2本を `import` して繋ぐことではない。数式と考え方が同じところは**自分でクラスを書き直し**、違うところは**同じ引数・同じ戻り値の別実装**として残す。クラス設計の分析は [docs/unified-blocks/](../unified-blocks/00_README.md) である。

問題は、上流が**完成した歩行器**であることである。標準のシミュレーションは、電源を入れた最初の周期から、ゲイト・予測最適化・下位トルク・（LC なら推定）を同時に回す。倒れたとき、接地が悪かったのか、力が悪かったのか、トルク変換が悪かったのか、切り分けられない。

一方で、四足の力学そのものは段階に分けられる。体重を支えること、足を上げること、前へ進むこと、速く走ること、坂や凸凹は、同時に理解しなくてよい。

そこで、自分のコードでは次のようにする。

- 先に、両リポに共通する式だけを動かす
- その上に、LC が持っていて PyMPC が薄いもの（推定、WBC、関節のハイブリッド指令）を足す
- その上に、PyMPC が持っていて LC が薄いもの（着地点のヒューリスティック、地形の推定、短い単剛体 MPC）を足す
- 速さ・坂・凸凹は最後に、一度に一つだけ足す

以下のうち、まだ Notebook で動かしていない段は**方針**である。上流が今日こう動いている、という記述だけが**実装事実**である。

---

## 2. 目的

1. 平地の静止から始め、動くコードを残したまま、理解する現象を一つずつ足す
2. 同じループの上で、割り算による力と、予測最適化による力を比較できる
3. LC と PyMPC を、別プロジェクトとして書き直さない。共通部分は使い回し、差は実装の差し替えにする
4. 高速歩行と不整地を、最初の目標にしない

新しいコントローラ系統を発明することが目的ではない。

---

## 3. 方針

### 3.1 ループの骨格を先に決める

制御の1周期を、次の呼び出しに固定する。中身は後から足す。呼び側は中を見ない。

```text
c   = ゲイト(時間)                 # 4脚が床に着いているか。0 か 1
grf = 脚力を決める(状態, c, 参照)    # 4脚 × 3軸の力（床から足へ）
tau = トルクにする(ヤコビ, grf)     # 関節 12
tau = 遊脚なら上書き(tau, c)       # 空中の脚は力では動かない
plant.step(トルクを飽和(tau))
```

これが再利用の意味である。上流のファイルを部品として挿すことではない。

予測最適化の生の入力ベクトル（PyMPC なら長さ 24 など）や、WBC の 42 個の決定変数を、この戻り値にしない。戻りが違うと、その下の行を全部書き直すことになる。

脚力 `grf` の単位と向きは文書で一つに固定する（SI、床から足）。

### 3.2 中身は足す。消さない

予測最適化や WBC を足すとき、それ以前の実装を上書き廃棄しない。同じ引数で切り替える。比較の相手がいなくなるからである。

一度に変えてよい中身は**一つ**である。同じ走行で「力の決め方もトルクの出し方も着地点も変えた」は、何が効いたか分からない。比較の表は [12](12_Block_Performance_Comparison.md) である。

### 3.3 一段に、新しい現象は一つ

倒れた理由を一つに帰せるときだけ、次へ進む。規則の詳細は [01](01_One_Difficulty.md) である。

速さ・坂・地面の欠け（足が落ちる穴）・凸凹は別の難しさである。同時に上げない。地図は [11](11_Difficulty_Map.md) である。

### 3.4 上流は読んでもコピーしない

OCS2 も acados の問題設定も、理解のために読む。自分の `src/` へファイルを移植しない。式が同じなら新しく書いてよい。

PyMPC の状態ベクトルと LC の状態ベクトルは、次元が似ていても中身が違う。一つの配列型に混ぜない。

参照軌道の作り方と、予測に使うモデルはセットで差し替える。LC の「1秒先の位置」を、PyMPC の「水平位置のコストがゼロの単剛体モデル」に繋がない。理由は [unified-blocks/06](../unified-blocks/06_Compose.md) である。

### 3.5 記述の区別

| 区分 | 意味 |
|---|---|
| **実装事実** | 上流コードまたは既存の学習ノートにそう書いてある |
| **理論** | その段階で使う式 |
| **方針** | 自分の Notebook での進め方。まだ動いた事実ではない |

「足踏みは予測最適化なしで書ける」「LC の次に PyMPC を足す」は方針である。上流の標準経路は最初の周期から予測最適化を呼ぶ（実装事実）。

### 3.6 コードは Notebook に書く

制御の計算（脚力、トルク変換、ゲイト、着地点、予測、推定、プラントへの指令）は **`src/` に書かない**。`src/` に隠すと、途中の数・符号・ヤコビの列・失敗した仮定が残らず、経緯が追えない。

**例外:** 図の描画、GIF、MuJoCo の起動や OpenGL など、**plot と環境の共通項**だけは `src/` に書いてよい。Notebook を短くするためである。制御の式は例外にしない。

実装環境は **uv** で作る。作成手順（Python 版、依存、同期コマンド）は Markdown に書く。口頭やチャットだけの手順にしない。

学習の本体は Notebook である。**リポジトリ根**の `notebook/` に `.ipynb` を直接置く（`docs/block-curriculum/` の下ではない）。Markdown から後で変換しない。各セルを実行しながら、[§7](#7-進め方) のフェーズを進める。教材デモ用の `docs/pympc_2day/notebooks/` とは別である。

ファイル名は連番にする。

```text
notebook/00_yy.ipynb
notebook/01_yy.ipynb
...
```

`xx` は二桁の通し番号、`yy` は内容の短い英語名である（例: `00_plant.ipynb`）。飛ばした番号は使わない。一つの Notebook は一段（一つの新しい現象または一つの差し替え）に対応させる。

各 Notebook には、次をこの順で書く。コマンドやコードだけを置かない。

1. **背景** — なぜこの段があるか。前の段との差。**成功条件をここで数値で固定する**（測る量、閾値、単位、連続時間）。後のセルで言い換えない
2. **目的** — この Notebook を終えたとき分かること、動いていること
3. **数式** — その段で使う式。手計算とコードが対応するように書く。不要なら書かない
4. **図** — データの流れや接地・力の図。文章だけでは追いづらいときに入れる
5. **コード** — 試行錯誤を **セルに書く**。途中の \(J\)、\(\tau\)、接地力を print して残す。**各コマンドに、意図と内容のコメントを付ける。** Notebook の目的は、コメントを読めばコードが分かることである。何を疑っているか、その行は何をするか、単位は何かを書く。コメント無しの式の羅列にしない
6. **思考過程** — 何を疑ったか、なぜその式にしたか
7. **仮説** — 次に試すこと。失敗したセルの直後にも書く
8. **結果と分析** — 成功でも失敗でも、何が式どおりで何が違ったか。**MuJoCo の GIF を必ず 1 個以上** Notebook に入れる（接地反力や胴体への合力など、分析に使う量）。失敗した走行でも GIF は必須である。ロボットの姿だけの映像にしない。GIF が無い Notebook は結果が無い

Notebook を上から読めば、**理論・計算・失敗・次の仮説**が追えるようにする。成功した最終版だけを残し、途中を `src/` に移して消す、はしない。

### 3.7 失敗は消さない

試行錯誤のすべてを Notebook に残す。失敗したセル、赤い出力、立たない GIF、誤った符号のログは、消さない。失敗ログが次の仮説の根拠である。

成功として次の番号へ進むのは、その段の目的が満たされたときだけである。失敗を残すことと、失敗を成功扱いすることとは別である。判定の数字と連続時間は [§3.8](#38-成功は数値で05-以降は-20-秒以上続ける) である。

この方針に切り替えるため、以前の import 型 Notebook は削除した。以降は本節で書く。

### 3.8 成功は数値で、05 以降は 20 秒以上続ける

各 Notebook の **背景** に、その段の成功条件を数値で書く。目視や「だいたい立った」では合格にしない。

1. **測る量を列挙する**（例: ベース高さ \(z\)、roll / pitch、並進速度、適用トルク、`qpos` が有限か）。単位を付ける
2. **閾値を書く**。実装しながら変えるなら、変えた理由をセルに残し、背景の数字も更新する
3. **判定はログの全ステップ**で行う。1 周期だけ閾値内、というのは不合格である
4. **連続時間。** \(00\)–\(04\)（プラント〜高さ P）は **5.0 秒以上**。\(05\) 以降は **20.0 秒以上**。連続時間は \(\mathrm{d}t\) に連続 True の最長区間を掛けたもの。足りなければ未成功
5. **06 以降で「歩く」段**（その場足踏みではない）は、連続時間に加えて水平移動 \(\lVert xy(T)-xy_0\rVert \ge 10.0\,\mathrm{m}\)
6. **05 以降のゲイト**は上流の足踏みに寄せる。許容から外れた duty 上げ・低周波数・数 mm リフトは、hold が長くても不合格
7. 未成功なら次の番号へ進まない。失敗したセル・GIF・数値ログは消さない
8. **1試行のサイクル。** 仮説を一つ変えた走行が終わったら、数値ログと **新しいファイル名の GIF** を残し、成功でも失敗でも commit して `origin/main` に push する。複数試行を溜めてからまとめて出さない。次の番号へ進むのは、背景の数値を満たしたあとだけである。詳細は [§3.8.1](#381-1試行ごとに-gif-を残しすぐ-push-する)

数値の一覧（変えたら当該 Notebook 背景も更新する）:

| 段 | 連続時間 | 歩行距離 | ゲイト |
|---|---|---|---|
| \(00\)–\(04\) | \(\ge 5.0\,\mathrm{s}\) | 求めない | — |
| \(05\) その場足踏み | \(\ge 20.0\,\mathrm{s}\) | その場（xy ドリフト上限は背景） | 下表の窓 |
| \(06\) 以降の歩くモード | \(\ge 20.0\,\mathrm{s}\) | \(\ge 10.0\,\mathrm{m}\) | 下表の窓。`full_stance` は 20 s 静止だけ |

上流の足踏み（PyMPC `gait_params`、LC `SwingTrajectoryPlanner`）と、この学習の許容:

| 量 | 参照 | 許容 |
|---|---|---|
| trot \(f\) | PyMPC \(1.35\,\mathrm{Hz}\) | \(\lvert f-1.35\rvert\le 0.15\,\mathrm{Hz}\) |
| trot duty | PyMPC \(0.74\) | \(\lvert d-0.74\rvert\le 0.06\) |
| 遊脚高さ | PyMPC \(0.2\times hip\_height=0.056\,\mathrm{m}\)、LC `swingHeight` \(0.08\,\mathrm{m}\) | \(0.045\le h_{\mathrm{step}}\le 0.090\,\mathrm{m}\) |
| crawl / pace / bound | PyMPC \(0.50/0.80\)、\(1.40/0.70\)、\(1.80/0.65\) | \(f\) は参照の 15%、duty は \(\pm 0.06\) |

「静止する」「追従する」段は、その状態が上の連続時間だけ保たれることである。着地の瞬間だけ良い、は失敗である。

プラント確認のように倒れてよい段でも、シミュレーションが **その段の連続時間以上進み**、その間の状態が背景の数値条件を満たすことをログで示す（例: 全ステップ `qpos` が有限）。走行そのものを短く切らない。

1試行が終わるたびに commit し origin に push する（[§3.8.1](#381-1試行ごとに-gif-を残しすぐ-push-する)）。次の番号へ進むのは、その番号の背景数値を満たしたあとだけである。git の可否は [§3.9](#39-破壊的でない-git-は行ってよい) である。

### 3.8.1 1試行ごとに GIF を残し、すぐ push する

1回の試行は、仮説を一つだけ変えた走行である。終わったら次をこの順で行う。複数の試行を溜めてからまとめて出さない。

1. その試行の数値ログ（hold、リフト、空中、姿勢、xy、歩く段なら距離）を Notebook に書く
2. その試行専用の **新しいファイル名** の GIF を残す。旧 GIF は消さない。接地反力（指令）と胴体合力 / \(mg\) を載せる
3. 成功でも失敗でも、その試行を commit し `origin/main` に push する。失敗を成功とは書かない
4. 背景の数値を満たしていなければ、次の番号へ進まない。同じ番号で次の試行へ戻る
5. 満たしたら、次の番号の最初の試行へ進む
6. フェーズ 0 の未完了段からフェーズ 3 の最後まで、このサイクルを止めない

### 3.9 破壊的でない git は行ってよい

この学習は、**各試行**（成功も失敗も）と、数値を満たした Notebook を `origin/main` に残す。普通の git を禁止しない。都度「commit してよいか」と聞かなくてよい。

**してよい（明示の再確認は不要）:**

- `git status`, `diff`, `log`, `show`, `fetch`
- `git add`（秘密情報は入れない）
- `git commit`
- `git push` / `git push -u origin HEAD` / `git push origin main`（`--force` も `--force-with-lease` も付けない）
- `git pull`（fast-forward を優先）

Auto-review が `origin/main` への上記の push を止めたときは、**同じコマンド**を承認付きでやり直す。push を省略しない。

**そのメッセージで明示されない限り、してはいけない:**

- force push（`--force`, `--force-with-lease`）
- `git reset --hard`
- 対話的な `rebase` など、入力待ちの git
- 条件を満たさない `git commit --amend`
- hook を飛ばす（`--no-verify`）
- `git config` を変える

## 4. 残すもの

次は学習の入口であり、予測最適化を足したあとの比較相手でもある。捨てない。

| 名前 | 中身 |
|---|---|
| `EqualShare` | 立脚で体重 \(mg\) を等分する。横力は 0。ホライズン無し |
| `HeightPdShare` | 上に、高さの比例・微分を足してから割る。ホライズン無し |
| `MapJT` | 仮想仕事 \(\tau_{\mathrm{map}}=-J^\top F\)。静止（\(\ddot q\approx 0\)）では 00 の運動方程式から \(\tau=h-J^\top F\)。\(h\) は重力とコリオリ（`qfrc_bias`）であり、キーフレームの関節 PD ではない |
| `PeriodicGait` | 位相・周波数・duty・脚ごとのずれ。トロットとペースの違いはここだけ |
| `SwingPath` と PD | 遊脚を空中の目標へ運ぶ |
| 着地点 = 今の水平位置 | その場足踏み・ごく遅い前進の初期 |
| シミュレータの真値 | 推定を足しても、切替の一方として残す |

PyMPC の標準コードに `EqualShare` は無い（実装事実）。自分の比較用に持つ。

## 5. どこを差し替えるか

骨格の各行に、複数の中身を置ける。平均しない。選んで呼ぶ。

| 関数 | 最初に置く中身 | LC を読む段で足す | PyMPC を読む段で足す |
|---|---|---|---|
| 脚力を決める | `EqualShare` | 長いホライズンの予測最適化（NMPC） | 短い単剛体モデル + acados |
| 力 → トルク | `MapJT` | 瞬間の全身 QP（`WeightedWbc`） | 最初の `MapJT` を使う |
| 今の状態 | シミュレータ真値 | 線形カルマンフィルタ | 真値のまま（PyMPC は推定しない） |
| 胴体の参照 | 高さと速度の定数 | 現在と最大 1 秒先の 2 点 | ホライズン中ほぼ一定の速度（水平位置は追わない） |
| 着地点 | 今の水平位置 | 増やさない | 速度に応じて先へ置くヒューリスティック |
| 床 | 水平 | 増やさない | 傾きの推定 |

LC の NMPC と PyMPC の acados は、どちらも「脚力を決める」の実装である。一つの MPC に潰さない。状態の定義もホライズンも違う。

`MapJT` と WBC も、どちらも「力（または目標）からトルク」だが中の式が違う。同時に初めて足さない。WBC を足しても `MapJT` は残す。

## 6. 上流は実行時に何をしているか（実装事実）

学習用の電源の入れ方ではない。完成した歩行器のデータの流れである。  
箱は処理、線はデータである。より詳しい境界は、PyMPC が [qpympc-study 00](../qpympc-study/00_README.md)、LC が [legged_control 00](../legged_control/00_README.md) である。

### 6.1 PyMPC

標準設定では、最初の周期から NMPC がいる。

立脚と遊脚は接地フラグ `c` で分岐する。ゲイト・着地点・地形は NMPC への入力であり、直列の三段ではない。

### 6.2 legged_control

胴体の速度指令とゲイト指令は、最初から別の枝である。推定は NMPC と WBC の両方へ入る。

  | Twist 4 または Pose 6            | ModeSequence

+------------------+          +------------------+

                        v

               | SqpMpc NMPC      |<----| KalmanFilter     |

                        v                        | IMU, q, 接地
               +------------------+              |

               | x*24, u*24, mode |              |

                        |                        |

## 7. 進め方

四つの塊に分ける。前の塊で書いた関数は、次の塊で消さない。

読むノートは、その塊で足す技術に限る。最初から両ディレクトリを通読しない。

実施は **MuJoCo** である。LC の Gazebo / 実機の章は読むが、この手順の走行と GIF は MuJoCo の四脚（Go2）で残す。

最初の Notebook は、MuJoCo 上で四脚ロボットが動くことの確認デモである。重力で潰れる、初期姿勢を保つ、など制御の正しさは問わない。フェーズ 0 の力の式より前に置く。

計算結果は、必ずその走行の **MuJoCo アニメーション GIF を 1 個以上** Notebook に入れる。GIF が無い段は終わっていない。表・グラフ・ログは補足である。GIF・描画の共通関数だけ `src/` にあってよい。制御のセルは Notebook に残す。

アニメーションには、見た目の歩行だけでなく **分析に使う量** を載せる。少なくとも次を、その段で意味があるものから出す。

- 各足の接地反力（指令。実接触が取れる段では指令と実測を色分けし、混ぜない）
- 胴体への合力・合モーメント（重力を含めるかは図のキャプションで明示する）
- その段の主題に応じたもの（遊脚なら足先軌道、坂なら床法線、など）

ロボットが動いている映像だけの GIF は、結果として足りない。

作業場所は **このリポジトリ `mpc_dog`（origin の `main`）** である。`external/` に機能を足さない。別クローンや一時フォルダで完結させない。

1試行が終わったら、その試行の GIF を残して commit し **origin に push** する（[§3.8.1](#381-1試行ごとに-gif-を残しすぐ-push-する)）。複数試行を溜めてからまとめて出さない。背景の数値を満たしていない試行を、成功としては push しない。これは破壊的でない git であり、[§3.9](#39-破壊的でない-git-は行ってよい) のとおり都度聞かずに行う。

うまく行かないときは、成功するまで試行錯誤する。その途中の失敗は Notebook から消さない。思考過程・次の仮説・成否の分析を書いてから次のセルへ進む。失敗を消した「きれいな成功だけ」の Notebook にしない。失敗したまま、分析も仮説も書かずに次の番号へ進むこともしない。背景の数値条件を満たさないまま次の番号へ進むこともしない。

本章（この README）に書いてある順で、フェーズ 0 からフェーズ 3 の最後まで実行する。途中の Markdown だけ読んで止めない。

### フェーズ 0 — 両リポに共通する式

予測最適化も WBC も状態推定も、着地点の先送りも、地形の推定も、まだ書かない。  
プラントの定義が要るときだけ [qpympc-study/01](../qpympc-study/01_MuJoCo_Go2_Plant_Model.md)、関節指令が要るときだけ [legged_control/07](../legged_control/07_Joint_Control_and_Hardware.md) を開く。

順番:

1. MuJoCo で四脚が動く確認デモ。GIF を Notebook に残す（`notebook/00`）
2. シミュレータが関節トルクを受けて次の状態を返す。トルクは上限で切る（`notebook/01`）
3. 4脚接地、体重を等分、仮想仕事 \(-J^\top F\)。静止では \(\tau=h-J^\top F\)。平地で **連続 5.0 秒以上** ほぼ静止する（`notebook/02`）。数値条件は Notebook の背景。満たすまで次の番号へ進まない
4. 高さの目標を足す（力の和が \(mg\) のままでは、高さは変わらない）。運動学は `notebook/03`。力の高さ P は次の番号
5. 周期ゲイトで足を上げる。遊脚は軌道追従。立脚は相変わらず \(J^\top F\)。**連続 20.0 s**。周波数・duty・遊脚高さは §3.8 の上流窓。duty を上げた直立は不合格（`notebook/05`）
6. トロットとペースなどは、ゲイトの数値（ずれ・duty・周波数）だけ変える。制御器を増やさない。**歩くモードは 20.0 s かつ 10 m**（`notebook/06`）
7. 前進。着地点は今の水平位置のまま。**20.0 s かつ 10 m**（`notebook/07`）
8. 「脚力を決める」の引数と戻りだけ決めておく。中身はまだ等分である。判定は 07 と同じ 20 s / 10 m

ここまでで分かること: 体重、遊脚、位相、遅い前進。分かっていないこと: 予測最適化、推定、WBC、不整地。

### フェーズ 1 — legged_control

ノートは [legged_control/00](../legged_control/00_README.md) の順（パッケージ → データフロー → 指令 → 推定 → NMPC → WBC → 関節）。  
フェーズ 0 の等分と \(J^\top F\) は残す。

順番:

1. 胴体指令とゲイト指令を別の入力にする
2. 線形カルマンフィルタで今の状態を出す。真値ソースは残す
3. 予測最適化は遅く（例: 100 Hz）、下位は速く（例: 500 Hz）。速い周期は、遅い解の「今この時刻の1点」だけを使う
4. NMPC を「脚力を決める」の二番目の中身にする
5. WBC を「トルクにする」の二番目の中身にする。`MapJT` は残す。この段で NMPC と WBC を同時に初めて比較しない
6. 関節は位置ゲイン 0、速度ゲイン固定、フィードフォワードがトルク（LC のハイブリッド指令）
7. 階層 WBC は読んで理解してよい。配線しない

LC の既定は、着地点の長い先送りも地形の平面推定も薄い。速さや坂はこのフェーズでは足さない。

### フェーズ 2 — PyMPC

ノートは [qpympc-study/00](../qpympc-study/00_README.md) から、データフロー（`02`）以降。標準の予測は `type=nominal` である。  
フェーズ 1 までの実装は残す。

順番:

1. 人の「前」をワールドへ回す。参照はホライズン中ほぼ一定の速度にする（水平位置は追わせない）。LC の 2 点参照は残し、つなぐモデルを変えるときだけ切り替える
2. 着地点を、速度と立脚時間から先へ置く
3. 床の傾きの推定、必要なら速度指令の変調
4. 短い単剛体モデル + acados を「脚力を決める」の三番目の中身にする。LC の NMPC と等分は残す
5. 立脚 \(-J^\top F\) と遊脚の直交 PD は、フェーズ 0 と同じ経路である。ここで新しい下位制御を発明しない
6. `sampling` と `lyapunov` は、`nominal` が同じ足踏み・同じ遅い前進でログに並んでから足す。設定の別値であり、別プロジェクトではない

### フェーズ 3 — 速さ、坂、凸凹、地面の欠け

予測もゲイトも下位も、すでにフェーズ 2 までにある。新しい層を足さない。指令の速さ、歩幅と周波数、摩擦、着地点、遊脚の高さ、床の傾きを、**一度に一つ**動かす。

### やってはいけないこと

- フェーズ 0 で acados や OCS2 を書く
- フェーズ 1 のあと、`MapJT` を消して PyMPC 用に作り直す
- WBC と acados を、同じ週にどちらも初めて入れる
- 上流パッケージを `import` して、上の順番を飛ばす
- フェーズ 1 のうちに速さ梯子や地形を始める
- 結果を表やグラフだけにして、MuJoCo の GIF を Notebook に入れない
- 結果の GIF を 1 個も Notebook に入れない
- コードに、各コマンドの意図と内容のコメントを書かない。コメントを読んでもコードが分からない書き方にする
- ロボットの姿だけで、接地反力や胴体合力を載せない GIF を結果にする
- この学習の走行を Gazebo で回す
- `external/` や別クローンだけに実装し、`mpc_dog` の `main` に戻さない
- 制御の本体を `src/` に移し、Notebook から import するだけにする（plot / 環境の共通項を除く）
- 失敗したセル・GIF・ログを消して、成功だけ残す
- 思考過程・次の仮説・成否の分析を書かずに次へ進む
- 背景に成功条件を数値で書かない / 書いた条件をログで確認しない
- 1 ステップや一瞬の値だけで合格にする。背景の連続時間未満（05 以降は 20.0 秒未満、歩く段は 10 m 未満）で次の番号へ進む。失敗試行を成功として push する
- エラーや未完成の GIF のまま、その Notebook を成功として次の番号へ進む / push する
- 複数試行を溜めてからまとめて GIF を作る / まとめて push する
- 試行のあとに GIF を作らず、次の仮説へ進む
- この README の途中で止める
- 破壊的な git（force push、`reset --hard`、対話的 rebase、無断の `git config` 変更）。普通の add / commit / `push origin main`（force なし）は止めてはいけない
