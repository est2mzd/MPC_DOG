# 抽出方針

## 1. 結論

`external/` は読み取り専用の参照実装として残す。自分のコードは `src/mpc_dog/` にだけ書く。ブロックは **式が閉じたものから** 切り、NMPC と QP-WBC は後回しにする。両リポの混成は、B00 の契約と数値テストが先である。

本章は方針である。実装事実は「上流をまだ変えない」「`src/` は空」である。

## 2. やってよいこと / やらないこと

### 2.1 やってよい

- 上流を読んで、入出力と式をノートとテストに固定する
- 短い核を自分のクラスとして書き直す
- 同一入力で上流関数と自分の関数の出力を照合する
- オーケストレータだけを自分で書く
- バックエンドを Protocol で差し替えられる形にする（中身は1個から）

### 2.2 やらない

- `external/` のファイルを `src/` へ丸コピーして「整理した」ことにする
- 上流の `config.py` や OCS2 型を自分の公開 API にする
- この段階で OCS2 をビルドして Python bind する
- 両方の NMPC を同時に保守する
- 上流のバグ（`joints_pos` に qvel index を渡す等）を再現する
- 標準 OFF の経路（VFA, sampling, Lyapunov, HierarchicalWbc）を第一版に入れる
- ドキュメントに無い「改良」を抽出と同時にやる（抽出と改善を混ぜない）

### 2.3 上流ライセンス（実装事実 + 注意）

両リポとも他者の OSS である。`src/` に移植・再実装したファイルには、元のライセンスと provenance（パス・コミット）を残す。ライセンス本文の解釈は法律判断ではない。コピーする前に各 README / LICENSE を読む。

## 3. 段階

各段階の完了条件は「ノートを増やすこと」ではなく **テストが通ること** である。

### Phase 0 — 契約（コードは型とテストだけ）

- B00: 脚順、状態インデックス、frame 名
- 上流レイアウト ↔ 自分のレイアウトの変換テスト（既知ベクトル）
- LC 脚名対応を URDF で1回確認し、[06](06_Interfaces_and_Contracts.md) の推測を事実に上げる

完了: `types` のテストが緑。歩行はまだしない。

### Phase 1 — 純計算ブロック

対象: B01, B03, B04, B05, B11, B12、B09 の `jacobian_transpose`、B10 の軌道関数。

完了: 各関数が上流の固定ケースと数値一致（atol は量ごとに決める）。

### Phase 2 — ループ再配置

- `loop/walking_loop.py` が PyMPC 標準と同じ順で Phase 1 を呼ぶ
- B08 は当面 **上流 `Acados_NMPC_Nominal` を adapters 経由で包む**
- B13 は `QuadrupedEnv` を包む
- 既存 workshop の平坦 trot（session01 相当）が転倒せず走る

完了: headless 8 s が既存スクリプトと qualitatively 同じ（距離・転倒なし）。完全一致は求めない（推測: 配線の差でビット一致は難しい）。

### Phase 3 — 補完ブロック

- B06 `linear_kf`。sim では `ground_truth` と並列比較できること
- B09 `weighted_qp`。Pinocchio + OSQP。平坦で Jacobian 転置より悪くないこと（基準は後で決める）
- B02 を LC の2点軌道としても書けること（まだループの既定にはしない）

完了: バックエンドを1フラグで切り替えられる。混成が「文章」ではなく実行できる。

### Phase 4 — B07/B08 を自分の管理下へ

- `dynamics/srbd.py` が CasADi / NumPy で `forward_dynamics` と一致
- acados OCP 構築を `src/` 側に移すか、生成コードの入口だけ自分で持つ
- `config` 相当は dataclass / YAML（`configs/` は既にある）

完了: `external/Quadruped-PyMPC` のコントローラを import せずに平坦 trot が走る。

### やらない段階（明示）

- OCS2 NMPC の Python 再実装
- 実機 ROS2 デプロイを `src/` の第一目標にすること
- 研究用 MPC 変異を全部移植すること

## 4. 照合のルール（方針）

1. テストは **上流の1関数** に対して書く。ループ全体のゴールデン GIF 比較は Phase 2 の補助だけ。
2. 乱数と codegen キャッシュを固定する。
3. 一致しなければ、自分のコードを疑う。上流を「直して」合わせない（抽出フェーズ）。
4. 一致しない理由が上流バグなら、自分の実装は正しい式を採用し、ノートに「差分」と書く。`joints_pos` がその例である。

照合に使う上流パスは 04 / 05 章の表である。

## 6. Cursor での作業単位（方針）

1回の作業で触るブロックは **1つ** を原則とする。渡す文脈:

1. 本ディレクトリの `00`, `03`, `08`, 本章
2. 対象ブロックの 04 または 05 の行
3. 対応する study 章（式）
4. 上流の該当 `.py` / `.cpp` だけ

リポジトリ全体と全 study 26 ファイルを毎回渡さない。

## 7. 成功の定義

「ブロックのように組み合わせて使える」は、次が同時に成り立つことである（方針）。

1. `gait`, `foothold`, `mpc`, `wbc` が互いに import しない
2. `loop` だけがそれらをコンストラクタで受け取る
3. B09 を `jacobian_transpose` から `weighted_qp` に差し替えても、B08 のコードを書き換えない
4. B06 を `ground_truth` から `linear_kf` に差し替えても、B03 を書き換えない
5. 各核に、上流または式に対する単体テストがある

今日の時点で 1–5 は満たしていない。満たすための道順が Phase 0–4 である。
