## 0. まず全体像:このロボットは何をしているのか

4本足のロボット(Go2)を歩かせたい。やることは大きく3つに分解できる。

1. **今どこにいて、どう動いているかを知る**(観測)
2. **次の一瞬(たとえば0.01秒後)、各足がどれくらいの力で地面を押せば、目標の速度で
   転ばずに歩けるかを計算する**(MPC = Model Predictive Control、モデル予測制御)
3. **その「力」を、実際にモーターへ送る「関節トルク」に変換する**(トルク変換)

これを1秒間に100回(`mpc_frequency=100`)繰り返す。これがこのリポジトリの制御ループの
すべてであり、以下の10ステップはこの3つの塊を実装レベルまで分解したものである。

**なぜ「力」を直接最適化するのか(MPCの発想)**: 関節角度を直接決めるのではなく、
「胴体(centroid、重心)にどんな力・モーメントが働けば目標の動きになるか」を先に決め、
そのために各足がどれだけ地面を押すべきかを最適化する。これを**Centroidal(重心)/SRBD
(Single Rigid Body Dynamics、単剛体力学)モデル**と呼ぶ。胴体を1つの剛体とみなし、
4本足からの反力だけで運動が決まると簡略化することで、リアルタイムで解ける最適化問題になる。
このモデルがステップ6に登場する。

**なぜ「予測」なのか(Predictiveの意味)**: 「今、この力を出したらどうなるか」だけでなく、
「これから0.5秒先まで、各足がいつ地面につくか(歩容=Gait)」を先読みし、その未来の接地計画を
考慮した上で、今この瞬間に出すべき力を決める。ただし実際に使うのは、計算した未来の計画のうち
**先頭の1ステップ分だけ**で、次の周期にまた同じ計算をやり直す。これを**Receding Horizon
(受け取っては捨てる、移動ホライズン)**と呼び、ステップ7→8の関係がこれにあたる。

以上を踏まえて、10ステップを順に読む。

## ステップ1: 今の状態を測る `simulation/simulation.py::run_simulation`

**背景**: 制御則がどんなに賢くても、今のロボットの位置・速度・関節角度が分からなければ
何も計算できない。ここはMuJoCo(物理シミュレータ)から「センサー値」を取り出す場所。
実機であれば、ここがモーションキャプチャやIMU・エンコーダからの読み取りに置き換わる。

**目的**: 制御周期1回分の「観測」をすべて集める。

- **Input**: MuJoCoのシミュレーション内部状態(`env.mjData`)。ユーザーが与える速度指令の
  種類(`base_vel_command_type`、既定`"human"` = キーボード操作)。
- **Process**: `env`(`QuadrupedEnv`)から次を読み出す:
  - 4本の足の位置・速度(world座標系)
  - 胴体(base)の位置・速度・向き・角速度(base速度はworld座標系、角速度はbase座標系 —
    ここが混在しているので注意)
  - 重心(CoM)位置
  - 目標速度(`env.target_base_vel()`)
  - 各関節の角度・角速度、脚のヤコビアン(関節速度→足先速度の変換行列)
- **Output**: 上記すべてを次のステップ(実際には内部でステップ2〜5をまとめて呼ぶ
  `quadrupedpympc_wrapper.compute_actions(...)`)へ引数として渡す。

**初心者がつまずきやすい点**: 「速度」や「位置」が world座標系(地面に固定)なのか
base座標系(ロボットの胴体に固定)なのかが変数ごとに違う。ここを読むときは、各変数の
frameを1つずつ確認しながら進めるとよい。

## ステップ2: 設定を確認する `quadruped_pympc/config.py`

**背景**: 「歩容はトロットかペースか」「MPCのホライズンは何ステップ先まで見るか」
「摩擦係数の上限は」といった、実験のたびに変える可能性のあるパラメータを1箇所にまとめてある。

**目的**: 以降のステップに出てくる`cfg.xxx`という変数がどこで定義されているかを知る。

- **Input**: なし(定数の定義ファイル)。
- **Process**: 大きく2つの辞書に分かれている。
  - `mpc_params`: MPCの中身に関わる設定(ホライズン長、ソルバーの種類、摩擦係数の上限・下限など)
  - `simulation_params`: シミュレーション側の設定(歩容の種類、制御周期、スイング脚の
    フィードバックゲインなど)
- **Output**: 他のすべてのファイルから`from quadruped_pympc import config as cfg`で
  参照される。

**読み方のコツ**: このファイルだけを最初から最後まで通読する必要はない。ステップ3以降を
読んでいて`cfg.mpc_params['horizon']`のような記述が出てきたら、そのたびにこのファイルへ
戻って値を確認する、という使い方でよい。

## ステップ3: いつどの足を地面につけるか決める `helpers/periodic_gait_generator.py`

**背景**: 4本足の動物・ロボットは、4本すべてを同時に浮かせることはできない(倒れる)。
「どの足をいつ地面につけるか」というスケジュール(歩容、Gait)を、力の最適化とは別に
先に決めておく必要がある。トロット(対角の2本ずつ交互)、ペース(左右2本ずつ交互)などの
パターンがある。

**目的**: 「今から先の時間、各足が接地しているかどうか」という0/1の時系列
(`contact_sequence`)を作る。

- **Input**: 各足の「位相」(0〜1で表した、1歩の周期の中の今どこにいるか)、
  歩行周波数(`step_freq`、既定1.35 Hz)、duty factor(1周期のうち何割接地しているか、
  既定0.74)。
- **Process**: 各足の位相を`位相 += dt × step_freq`で進め、位相が`duty_factor`未満なら
  接地(1)、それ以上なら遊脚(0)と判定する。この「位相を進める→判定する」処理を、
  今の位相を保存してから何十ステップも先読みし、最後に元の位相へ戻す、という形で
  「未来の接地スケジュール」を作る(副作用なしの先読み)。
  トロットでは4本足の位相にあらかじめ`[0.5, 1.0, 1.0, 0.5]`のズレ(offset)を与えることで、
  対角の2本が同時に接地・浮遊するパターンを作る。
- **Output**: `contact_sequence`(4本足 × ホライズン長の0/1配列)。この配列の**1列目
  (今この瞬間)**が`current_contact`として使われ、それ以外の列(未来)がステップ6・7の
  MPCの中で「未来のどの時点でどの足が使えるか」の材料になる。

**次のステップとのつながり**: この`contact_sequence`は、ステップ6の運動方程式の中で
「決定変数」ではなく「外から与えられた既知の値(パラメータ)」として使われる。つまり
MPCは「どの足をいつ着けるか」は最適化せず、すでに決まったスケジュールを前提に
「その足がどれだけの力を出すか」だけを最適化する。この役割分担を先に理解しておくことが、
ステップ6を正しく読むための鍵になる。

## ステップ4: どこに足を下ろすか決める `helpers/foothold_reference_generator.py`

**背景**: 「いつ」足を下ろすかはステップ3で決まった。次は「どこに」下ろすかを決める必要が
ある。これを直感的な公式(Raibertヒューリスティックと呼ばれる、1980年代からある古典的な
考え方)で計算する。MPCの最適化とは別の、比較的単純な幾何計算。

**目的**: 各足の「着地目標位置」(`ref_feet_pos`)を計算する。

- **Input**: 胴体の位置・向き、現在の速度、目標速度、股関節(hip)の位置。
- **Process**: 直感的には「今の股関節の真下」を基準にして、
  1. 目標速度が速いほど、足を大きく前(または後ろ)にずらす
     (`(接地時間/2) × 目標速度`だけずらす。「半歩分だけ、速度に比例してずらす」という発想)
  2. 実際の速度が目標速度から遅れている/進みすぎている分を、追加で補正する
     (振り子の周期の考え方を使った補正項)
  3. 左右方向には、股関節から少し外側(`hip_offset=0.1m`固定)にずらして、足が
     胴体の真下に来て自分同士でぶつからないようにする
- **Output**: `ref_feet_pos`(4本足それぞれの、world座標系での目標着地位置)。この値は
  ステップ5で`ref_state`辞書に格納され、ステップ7のMPCのコスト関数の「参照値」
  (=これに近づけたい目標)として使われる。

**このステップがステップ3の後にある理由**: 「今の足がいつ地面から離れたか
(lift-off)」「いつ地面についたか(touch-down)」を検出するには、ステップ3の
`current_contact`(今の接地状態)と、1つ前の周期の接地状態(`previous_contact`)を
比較する必要があるため。

## ステップ5: 全部の情報を1つにまとめる `interfaces/wb_interface.py::update_state_and_reference`

**背景**: ここまでのステップ1(観測)・3(歩容)・4(着地目標)はそれぞれ別の場所で
別の形式のデータを作ってきた。MPC(ステップ6・7)はこれらを1つの決まった形式
(辞書)として受け取りたい。この変換・集約をやるのがこの関数。いわば「のりしろ」の役割。

**目的**: ステップ6・7が直接使う3点セット、`state_current`(今の状態)・`ref_state`
(目標の状態)・`contact_sequence`(接地スケジュール)を組み立てる。

- **Input**: ステップ1の観測一式、ステップ3の`contact_sequence`、ステップ4の`ref_feet_pos`。
- **Process**:
  - ステップ3(`self.pgg.run(...)`)とステップ4
    (`self.frg.compute_footholds_reference(...)`)をこの関数の中から呼び出す
    (つまりステップ3・4は独立した処理ではなく、この関数に埋め込まれている)。
  - 今の状態を`state_current`という辞書にまとめる。ここで**要注意な点**が2つある:
    - `position`には胴体位置ではなく**重心(CoM)位置**が入る
    - `linear_velocity`には重心速度ではなく**胴体(base)の速度**が入る
    - つまり「位置」と「速度」で基準点が違う、という非対称性がある(実装上のことで、
      理論的に正しい設計というより実装の現状としてそうなっている)
  - 目標状態を`ref_state`という辞書にまとめる。地形の傾き(roll/pitch)を推定し、
    目標速度をその傾きに合わせて回転させる補正も入る。
- **Output**: `state_current`, `ref_state`, `contact_sequence`。これらがそのまま
  ステップ6・7へ渡される。

**このステップを飛ばして次に進んではいけない理由**: ステップ6・7を読んでいて
「`position`ってCoM?胴体?」と迷ったら、答えは必ずここにある。先に読んでおかないと、
MPCのコスト関数(ステップ7)が何を「誤差」として計算しているのか誤解する。

## ステップ6: 物理モデルを作る `controllers/gradient/nominal/centroidal_model_nominal.py`

**背景**: MPCが「未来を予測」するには、「今こういう力を出したら、次の瞬間どうなるか」を
表す数式(運動方程式)が要る。4本足のロボット全体を関節レベルで正確にモデル化すると
計算が重すぎて実時間では解けないので、「胴体を1つの剛体とみなし、4本の足からの
反力だけが作用する」という単純化(Centroidal/SRBDモデル)を使う。

**目的**: CasADi(数式を記号のまま扱うライブラリ)で「状態が今こうで、こういう力を
加えたら、次の瞬間の状態はこうなる」という関数を定義する。

- **Input(状態、30個の数値)**: 重心位置(3)・重心速度(3)・姿勢角roll/pitch/yaw(3)・
  角速度(3)・4本足の位置(3×4=12)・積分項(6、後述)。
- **Input(入力、24個の数値)**: 4本足それぞれの速度(3×4=12、遊脚のときだけ意味を持つ)と
  4本足それぞれが地面を押す力(GRF, Ground Reaction Force、3×4=12)。**MPCが最終的に
  決めたいのはこの「力」の部分**である。
- **Input(パラメータ、29個の数値)**: 各足が接地しているかどうか(0/1、ステップ3の
  `contact_sequence`から)、摩擦係数、慣性行列、質量など。パラメータは「状態」や
  「入力」と違い、**最適化の対象ではなく、外から与えられて固定される値**。
- **Process(運動方程式、物理の中身)**:
  - 並進運動: 「重心の加速度 = (各足の力 × その足が接地しているか) の合計 ÷ 質量 + 重力」。
    接地していない足(`stance_i=0`)は式の上で自動的に効かなくなる(0を掛けるので)。
  - 回転運動: 「角加速度 = 慣性行列の逆行列 × (各足の力が重心まわりに作るモーメントの合計
    − 角速度に起因する慣性項)」という、剛体の回転の基本法則(オイラーの運動方程式)。
  - 足の位置: 接地中の足は「動かない」という前提(速度を強制的に0にする)。遊脚中の足だけ、
    実際の足速度がそのまま使われる。
  - 積分項: 「重心のz位置や速度、roll/pitchの角度を時間積分したもの」を追加の状態として
    持たせている。これは後述するがステップ7のコスト関数で使われ、定常偏差を抑える
    (PID制御でいう「I項」に相当する役割)。
- **Output**: `forward_dynamics()`という、状態・入力・パラメータを受け取って
  「次の瞬間の状態変化率」を返すCasADi関数。これがそのままステップ7のacados
  (数値最適化ソルバー)に渡され、「未来を予測する数式」として使われる。

**初心者向けの一言**: 「状態」と「入力」と「パラメータ」の違いに慣れることが、
この章を理解する最大のポイント。「状態」はMPCが予測する対象、「入力」はMPCが
決める対象(=最終的に欲しい答え)、「パラメータ」はMPCの外(歩容・地形・ロボットの
物性値)からすでに決まって渡されてくる値、と覚えるとよい。

## ステップ7: 最適な力を計算する `controllers/gradient/nominal/centroidal_nmpc_nominal.py`

**背景**: ステップ6で「物理法則」は用意できた。あとは「どんな力を出せば一番良いか」を
決める必要がある。「一番良い」を数式にしたものが**コスト関数**(目的関数)、
「絶対に守らないといけない条件」を数式にしたものが**制約**である。この2つを合わせて
「最適化問題」として定式化し、専用のソルバー(acados)に解かせる。

**目的**: 「目標の速度・姿勢にできるだけ近づきつつ、無理な力を出さず、地面から
足が滑ったり浮いたりしない」という条件のもとで、最も良い力の時系列を計算する。

- **Input**: ステップ5の`state_current`(今の状態)・`ref_state`(目標)、
  ステップ6の運動方程式、ステップ3の`contact_sequence`(未来の接地スケジュール)。
- **Process**:
  - **コスト関数**: 「状態が目標からどれだけずれているか」を、状態ごとに異なる
    重み(どれだけ気にするか)をつけて足し合わせる。実際の重みを見ると:
    - 重心のx,y位置のずれには**重みが0**(気にしない)、z位置(高さ)には強い重み
    - 速度のずれには中程度の重み
    - roll/pitch角のずれには強い重み、yaw角には**重みが0**(気にしない)
    - 4本足それぞれの目標着地位置(ステップ4の`ref_feet_pos`)からのずれにも重み
    - つまりこのMPCは「胴体の高さと傾きは厳密に保つが、水平位置と向き(yaw)は
      速度さえ合っていれば多少ずれてもよい」という設計思想になっている。
    - 最後の瞬間(予測ホライズンの一番先)にも同じ重みを使う(終端専用の特別な重みは無い)。
  - **摩擦の制約**: 「足が地面を押す力」が、摩擦円錐(足がスリップしない範囲)に
    収まっているかを、4本足×5本の不等式(合計20本)で表現する。「垂直方向の力は
    最小値〜最大値の間」「水平方向の力は摩擦係数×垂直力を超えない」という条件。
  - **求解**: 上記を「非線形計画問題」として定式化し、acados(専用の高速ソルバー)で
    解く。設定によってSQP(逐次二次計画法)、SQP_RTI(リアルタイム反復、実機向けに速い)、
    DDP(微分動的計画法)などのアルゴリズムを切り替えられる。
- **Output**: 予測ホライズン全体(たとえば0.5秒先まで)にわたる、状態と力の時系列。
  ただし実際に使うのは、この中の**一番最初の1ステップ分の力**だけ(これが次の
  ステップ8で取り出される)。

**初心者向けの一言**: 「コスト関数の重みが0の項目=そこは自由に動いてよい、という
設計判断」と読み替えると、パラメータの意味が理解しやすい。x,y位置とyawの重みが0、
というのは「まっすぐ歩く」ことよりも「指定した速度で歩く」ことを優先する設計、と解釈できる。

## ステップ8: 「今使う分」だけを取り出す `interfaces/srbd_controller_interface.py`

**背景**: ステップ7のMPCは「未来何十ステップ分」の答えをまとめて返してくる。しかし
実際にロボットへ送るべき指令は「今この瞬間」の1つだけである(Receding Horizonの考え方)。
また、MPCが解いた力は数値計算上ゼロにならないことがあるため、念のためもう一段
「今、接地していない足の力は強制的にゼロにする」という安全策も入っている。

**目的**: MPCの答えから「今使う1ステップ分の力」を取り出し、遊脚の力を確実にゼロにする。

- **Input**: ステップ7のMPCが返す力の時系列(先頭ステップ分)、ステップ3の
  `current_contact`(今この瞬間、どの足が接地しているか)。
- **Process**: 先頭ステップ分の力(4本足×3成分=12個の数値)を取り出し、
  「その足が今接地していなければ、力に0を掛ける」という掛け算を行う
  (`力 = MPCの解 × 接地フラグ(0 or 1)`)。
- **Output**: `nmpc_GRFs`(4本足それぞれの、今使うべき地面反力)。ステップ9へ渡される。

**このステップの位置づけ**: ステップ7のコスト関数・制約は「予測ホライズン全体」を
扱う複雑な計算だったが、ここは単純に「先頭だけ取り出して、念のためもう一度マスクする」
という短い処理。複雑な最適化(ステップ7)と、単純なトルク変換(ステップ9)の間の
「橋渡し」だと考えるとよい。

## ステップ9: 力を関節トルクに変換する `interfaces/wb_interface.py::compute_stance_and_swing_torque`

**背景**: ステップ8までで「各足が地面を押すべき力(3次元ベクトル)」が決まった。しかし
モーターが実際に受け取れる指令は「関節トルク」(回転力)である。「足先に働く力」から
「関節のトルク」への変換が必要になる。また、地面についていない足(遊脚中)は
そもそも押す力を計算する意味がないので、代わりに「次に着地する場所へ向けて足を
振り出す」ための、別の制御(軌道追従)が必要になる。

**目的**: 立脚中の足には力をトルクに変換する計算を、遊脚中の足には振り出し軌道を
追従させる計算を、それぞれ適用して最終的な関節トルクを得る。

- **Input**: ステップ8の`nmpc_GRFs`(地面反力)、ステップ4/8の`nmpc_footholds`
  (目標着地点)、脚のヤコビアン(ステップ1で取得)、現在の関節角度・角速度。
- **Process**:
  - **立脚中の足**: 「関節トルク = −(ヤコビアンの転置) × 地面反力」という式で変換する。
    ヤコビアンは「関節が動いたときに足先がどう動くか」を表す行列なので、その転置を
    使うと逆に「足先に働かせたい力」を「関節トルク」に変換できる(仮想仕事の原理)。
    PD制御のような追加のフィードバック項は**無い**(このコード上の事実であり、
    「本来こうあるべき」という話ではない点に注意)。
  - **遊脚中の足**: 「離陸した場所」から「目標着地点」まで、滑らかな軌道
    (スイング軌道)を作り、その軌道に対してPD制御(目標位置・速度との差を
    フィードバックする制御)で足を動かすためのトルクを計算する。
  - 摩擦補償: 設定によっては、関節の摩擦力を打ち消す項を全部の足(立脚・遊脚問わず)に
    追加する。
  - 逆運動学: 目標の足先位置から、目標の関節角度を数値的に逆算する(モーター位置制御の
    目標値として使うため。ただしこのコードでは実際にはコメントアウトされていて
    使われていない箇所がある)。
  - 安全のためのクリップ: 目標関節角度・速度が、現在の値から大きく離れすぎないように
    上限を設ける。
- **Output**: `tau`(4本足×3関節=12個の関節トルク)。ステップ10へ渡される。

**初心者がつまずきやすい点**: 立脚と遊脚で、まったく異なる2つの制御則が
1本のコードの中で`if`文によって切り替わっている。「今読んでいるのは立脚の話か、
遊脚の話か」を常に意識しながら読むとよい。

## ステップ10: モーターを動かし、シミュレーションを1歩進める `simulation/simulation.py`(ステップ1と同じファイル)

**背景**: 計算した関節トルクを、実際に(このリポジトリではMuJoCo物理エンジンに)
送らなければ何も起こらない。ここが「頭の中の計算」と「実際にロボットが動く」を
つなぐ最後の場所。

**目的**: トルクを安全な範囲に収めてからモーターへ送り、物理シミュレーションを1ステップ
進める。

- **Input**: ステップ9で計算した`tau`(関節トルク)。
- **Process**: モーターが出せる最大トルクの90%を上限としてクリップする(モーターの
  能力を超えないように、かつ少し余裕を残す安全マージン)。その後、MuJoCoの`env.step()`を
  呼んで物理シミュレーションを1ステップ(たとえば0.002秒)進める。
- **Output**: 新しいロボットの状態(位置・速度・関節角度など)。これが**次の制御周期の
  ステップ1の入力になる**ことで、ループが閉じる。

**全体を振り返って**: ステップ1〜10を1周すると、「観測→歩容計画→着地点計画→
状態集約→物理モデル→最適化→取り出し→トルク変換→実行」という一連の処理が完了し、
再びステップ1に戻る。このループが1秒間に数百回(シミュレーションの`dt`次第)回り続けることで、
ロボットが歩き続ける。

## この順番で読むべき理由のまとめ(1枚で振り返る)

| 前のステップ | 次のステップ | つながりの中身 |
|---|---|---|
| 3(歩容) | 6(物理モデル) | `contact_sequence`が力学の「パラメータ」として使われる。歩容が先に決まっていないと、力学モデルの`stance_i`という係数の意味が分からない |
| 4(着地点) | 5(集約) | 着地点の計算にはステップ3の接地状態の切り替わり(lift-off/touch-down)の検出が要る |
| 1・3・4 | 5(集約) | 別々に計算された値を、MPCが読める1つの辞書形式にまとめる「のりしろ」 |
| 5(集約) | 6・7(モデル・MPC) | `state_current`/`ref_state`の中身(何がCoMで何がbase速度か)を知らないと、コスト関数が何を最小化しているか誤解する |
| 6(物理モデル) | 7(MPC定式化) | コスト関数の重み配列は、ステップ6で定義した状態の並び順(30個)にそのまま対応している |
| 7(MPC) | 8(取り出し) | MPCは未来全体を計算するが、使うのは先頭の1ステップだけ(Receding Horizon) |
| 8(取り出し) | 9(トルク変換) | 「力」から「トルク」への変換は、力が確定してからでないとできない |
| 9(トルク変換) | 10(実行) | 最終出力(トルク)を安全範囲に収めてから初めてモーターに送れる |
| 10(実行) | 1(観測) | シミュレーションが1歩進んだ結果が、次の周期の観測になる(ループが閉じる) |

各ステップの行番号つきの詳細な根拠は[07_code_reading_order_v1.md](07_code_reading_order_v1.md)、
さらに深掘りしたい章は本フォルダの`01`〜`06`および`docs/qpympc-study/`を参照。
